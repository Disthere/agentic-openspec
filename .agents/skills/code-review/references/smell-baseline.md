# Базлайн запахов кода (judgement calls)

Фиксированный набор эвристик из «Refactoring» (Фаулер, гл. 3). Он действует, даже если репозиторий ничего
не документирует, и передаётся оси Standards в промпте дословно.

## Два связывающих правила

1. **Стандарт репозитория главнее.** Задокументированное правило проекта отменяет запах: где стандарт
   предписывает практику, которую базлайн бы пометил, находка **подавляется**. Примеры для этого
   репозитория: запрет LINQ в горячих путях ([`01-code-style.md`](../../../../openspec/standards/01-code-style.md))
   отменяет «замени цикл пайплайном»; требование `ProblemDetails` для ошибок отменяет претензии к
   «единообразию ответов»; конвенция DI делает регистрационные обёртки нормальными, а не «Middle Man».
2. **Всегда judgement call.** Каждый пункт — помеченная эвристика («возможный Feature Envy»), а не
   жёсткое нарушение. Подавляй только то, что **доказано покрыто инструментами** (анализаторы, `dotnet format`);
   смысловые случаи разбирай, а не отбрасывай.

Запахи **не блокируют** приёмку: они не могут дать `VERDICT: Fail`. Блокируют нарушение задокументированного
стандарта, невыполненное требование и нарушение обязательного правила проекта.

Как читать: *что это* → *как чинить*.

## Именование и понимание

- **Mysterious Name.** Имя функции, переменной или типа не сообщает, что он делает или хранит. → Переименуй;
  если честного имени не находится — мутный сам дизайн, а не имя.
- **Comments as deodorant.** Комментарий объясняет *что*, потому что код непонятен. → Сделай код
  самоочевидным; комментарий оставь для *почему* (ограничения, инварианты, ссылка на требование).
- **Long Parameter List.** Больше трёх-четырёх параметров, особенно рядом однотипных. → Собери параметр-объект
  (`record`), передавай зависимость целиком или разбей функцию.

## Дублирование и структура

- **Duplicated Code.** Одна и та же форма логики встречается в нескольких местах диффа. → Выдели общую форму
  и вызывай её; не оставляй копию «пока».
- **Long Function.** Функция не помещается в один экран и требует комментариев-разделителей. → Извлеки шаги
  с говорящими именами; тело оставь как последовательность намерений.
- **Data Clumps.** Одни и те же группы полей ходят вместе (`street`, `city`, `zip`). → Собери в `record`/тип
  значения и передавай его.
- **Primitive Obsession.** `string`, `int`, `decimal` вместо доменного типа (`Money`, `OrderId`). → Введи тип
  значения с валидацией в конструкторе.
- **Repeated Switches.** Один и тот же `switch` по типу/статусу повторяется в разных местах. → Полиморфизм
  или таблица стратегий; в C# — pattern matching в одном месте.
- **Loops.** Ручной цикл вместо декларативной операции там, где производительность не критична. →
  Пайплайн LINQ вне горячих путей; **в горячих путях цикл — правильный выбор**, запах не применяется.
- **Large Class.** Класс накапливает несколько ответственностей. → Раздели по ответственности, а не по размеру.

## Связность и ответственность

- **Divergent Change.** Один модуль меняется по нескольким независимым причинам. → Раздели причины изменения
  по модулям.
- **Shotgun Surgery.** Одно изменение требует правок во многих файлах. → Собери логику в один модуль.
- **Feature Envy.** Метод больше работает с данными чужого объекта, чем своего. → Перенеси метод к тем данным.
- **Insider Trading.** Модули втихую обмениваются внутренними данными. → Открой явный интерфейс или объедини модули.
- **Message Chains.** `a.B().C().D()` — вызывающий зависит от всей цепочки. → Спрячь обход за одним методом
  первого объекта.
- **Middle Man.** Класс или функция почти только делегирует дальше. → Убери его и вызывай цель напрямую.
- **Lazy Element.** Тип или функция не окупает существование (обёртка ради обёртки). → Удали.
- **Speculative Generality.** Абстракция, расширяемость и параметры «на будущее». → Убери, пока нет второго
  реального применения; правило «один адаптер — гипотетический шов, два — настоящий».
- **Temporary Field.** Поле заполняется лишь иногда и пустует в остальное время. → Вынеси в отдельный тип
  или передавай параметром.

## Данные и мутабельность

- **Global Data.** Изменяемое состояние, доступное отовсюду (статические поля, синглтоны-состояния). →
  Передавай зависимость явно; неизменяемое — `static readonly` или константа.
- **Mutable Data.** Данные меняются там, где достаточно прочитать. → `record`, `init`, `readonly`; изменения —
  через новые значения.
- **Data Class.** Класс только с полями и без поведения. → Перенеси к нему поведение, которое работает с этими
  полями (или признай его DTO и не добавляй логику в другое место).

## Наследование и интерфейсы

- **Refused Bequest.** Наследник игнорирует или переопределяет почти всё унаследованное. → Откажись от
  наследования в пользу композиции.
- **Alternative Classes with Different Interfaces.** Два класса делают одно и то же с разными сигнатурами. →
  Сведи к одному интерфейсу и переименуй методы одинаково.
