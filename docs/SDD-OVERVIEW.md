# Как устроена эта SDD-модель — краткий обзор

Документ для человека: что это за модель, из чего она состоит, кто что делает и в каком порядке.
Детали — в [`openspec/constitution.md`](../openspec/constitution.md) (высший приоритет) и
[`AGENTS.md`](../AGENTS.md) (канон правил для агентов).

---

## 1. Суть в одном абзаце

Это **Spec-Driven Development** — разработка, где код пишется не «по намерению в голове», а по
утверждённой спецификации. Каждое изменение проходит одинаковый путь: разобраться в задаче →
написать спецификацию → утвердить её человеком → реализовать → доказать уликами → проверить
независимо → выпустить → заархивировать. Модель не даёт агенту «просто начать кодить»: между
идеей и первой строкой кода стоит гейт.

Работает это в **DeepSeek Harness**: главная сессия — Оркестратор, она делегирует задачи
субагентам с ролью. Роли описаны файлами в `.agents/`, а не зашиты в промпт.

---

## 2. Из чего состоит

| Слой | Где | Зачем |
| - | - | - |
| **Конституция** | [`openspec/constitution.md`](../openspec/constitution.md) | Высший приоритет. Границы сервисов, гейты, фазы |
| **Канон правил** | [`AGENTS.md`](../AGENTS.md) | Что агент обязан соблюдать: C#, тесты, процесс, guardrails |
| **Стандарты** | [`openspec/standards/`](../openspec/standards) | 12 документов: стиль кода, архитектура, API, безопасность, производительность… |
| **Роли** | [`.agents/*.md`](../.agents) | Шесть ролей: миссия, входы, артефакты, критерии готовности |
| **Скиллы** | [`.agents/skills/`](../.agents/skills) | Переиспользуемые процедуры: `spec-first`, `code-review`, `implement-feature` |
| **Профиль проекта** | [`openspec/config.yaml`](../openspec/config.yaml) | Стек, активная схема, 10 фаз, **команды гейта** |
| **Спецификации** | [`openspec/specs/`](../openspec/specs) | Живые требования: что система должна делать сейчас |
| **Предложения** | [`openspec/proposals/`](../openspec/proposals) | Изменения «в полёте» и архив завершённых |
| **Машинные гейты** | [`tools/`](../tools) | Скрипты, которые проверяют вместо человека |

Ключевая мысль: **у каждого правила один источник**. Команды сборки — только в `config.yaml`,
фазы — только в конституции. Остальные документы ссылаются, а не переписывают.

---

## 3. Шесть ролей

Роли идут конвейером; каждая передаёт результат следующей.

| Роль | Фаза | Что делает | Чего НЕ делает |
| - | - | - | - |
| **Аналитик** | Discovery | Разбирает материалы в `inputs/`, регистрирует их как `IN-NNN`, формулирует проблему, ценность и **измеримый** критерий успеха | Не пишет спецификации и код |
| **Архитектор** | Spec, Design | Превращает задачу в `proposal.md` с требованиями и сценариями, рисует C4/Mermaid | Не пишет реализацию |
| **Разработчик** | Build | Реализует **только** задачи из `tasks.md`, гоняет `dotnet build/test/format` | Не меняет требования |
| **Инженер верификации (QA)** | Verify | Добывает **независимые** улики, заполняет `acceptance.md` | Не правит код; не подтверждает слова автора |
| **Ревьюер** | Review | Двухосевое ревью: соответствие стандартам **и** спецификации. Один вердикт `Pass`/`Fail` | Не правит код; не тот, кто писал |
| **Ops / Release** | Release, Operate, Feedback | Changelog, SemVer, план отката, SLO, runbook | Не пишет продуктовый код |

Есть два «служебных» участника: **Оркестратор** (главная сессия — планирует, делегирует, разрешает
конфликты, архивирует) и **человек-владелец** (утверждает спецификации, принимает решения на гейтах).

---

## 4. Последовательность работы

Десять фаз. У каждой есть **артефакт** (что остаётся на диске), **гейт** (что должно быть
выполнено) и **владелец** (кто отвечает).

```
Discovery → Spec → Design → Build → Verify → Review → Release → Operate → Feedback → Archive
```

| # | Фаза | Что появляется на диске | Гейт |
| - | - | - | - |
| 1 | **Discovery** | `inputs/INDEX.md` с записями `IN-NNN`, измеримый критерий успеха | Материал зарегистрирован, критерий измерим, нерешённое → `OQ-N` |
| 2 | **Spec** | `openspec/proposals/<NNN-slug>/proposal.md` | **Человек поставил `Status: Approved`** |
| 3 | **Design** | `design.md`, `contracts/`, ADR | Архитектурное решение зафиксировано |
| 4 | **Build** | `src/`, `tests/` | `dotnet build` / `test` / `format` зелёные |
| 5 | **Verify** | `acceptance.md`, `performance.md` | Улики воспроизводимы и добыты **не** автором кода |
| 6 | **Review** | Вердикт ревью | `VERDICT: Pass` по двум осям |
| 7 | **Release** | `CHANGELOG.md`, версия, миграции, план отката | DoD 5.4 |
| 8 | **Operate** | SLO, capacity, runbook | Health-checks и алерты готовы |
| 9 | **Feedback** | `OQ-N` или новое предложение | Инцидент стал отслеживаемым пунктом |
| 10 | **Archive** | Дельты влиты в `specs/`, предложение в `archive/` | Чекбоксы закрыты, `Status: Done` |

**Фазы не пропускаются.** Гейт без артефакта не вводится: если условие нельзя подтвердить файлом,
это пункт чек-листа, а не гейт.

## 5. Что лежит в предложении

`proposal.md` — центральный документ. Обязательные разделы (их проверяет скрипт):

| Раздел | Смысл |
| - | - |
| `Context` | Почему это нужно сейчас |
| `Requirements` | Требования с ID, у каждого — минимум один сценарий `WHEN/THEN` |
| `C# Implementation Plan` | Как будем делать и **какие новые зависимости** |
| `API / Contract Changes` | Что меняется в публичных контрактах |
| `Test Strategy` | Чем докажем, что работает |
| `Capabilities` | Какие возможности затрагиваем |
| `Impact` | Что сломается / кого затронет |
| `Changelog` | Какую запись добавим в историю |

Плюс соседние файлы: `tasks.md` (чек-лист `- [ ] 1.1 …`), `acceptance.md` (матрица
«требование → тест → результат»), `performance.md` (если речь о скорости), `specs/<capability>/spec.md`
(дельты требований).

**Ключевые слова `ADDED`, `Requirement`, `Scenario`, `WHEN`, `THEN` — только на английском.**
Перевод ломает схему валидации.

## 6. Мелкие изменения не платят полную цену

Полный цикл для правки в один файл — избыточен. Поэтому есть **лёгкий маршрут `lite`**, но он
допустим только при **всех** условиях сразу:

- ≤ 2 файлов;
- ≤ 50 строк;
- не меняются публичные контракты;
- не меняется видимое пользователю поведение.

В `lite` в предложении достаточно `Context`, `Change`, `Test Strategy`, `Impact`, `Changelog`,
а требований и дельт спецификаций не нужно. **Даже в `lite` обязательны**: запись в changelog,
тесты для изменённой логики и проверка командами.

Нарушено хотя бы одно условие — полный цикл, без обсуждения.

---

## 7. Почему модель можно проверить, а не только «надеяться»

Главный принцип: **проверка = команда, а не суждение.** Всё, что можно проверить машиной, проверяется
машиной:

| Скрипт | Что ловит |
| - | - |
| [`tools/validate-proposals.ps1`](../tools/validate-proposals.ps1) | Структуру предложений: разделы, сценарии, паритет с `specs/`, битые ссылки, `lite` |
| [`tools/check-canon-parity.ps1`](../tools/check-canon-parity.ps1) | Расхождение правил между `AGENTS.md` и зеркалом `.clinerules` |
| [`tools/check-template-clean.ps1`](../tools/check-template-clean.ps1) | Что в шаблон не просочилась история самого набора |
| [`docs/ci/check-dsh-profile.ps1`](../docs/ci/check-dsh-profile.ps1) | Что пресет роли действительно имеет инструменты |
| [`.github/workflows/scaffold-check.yml`](../.github/workflows/scaffold-check.yml) | Всё вышеперечисленное + `dotnet build/test/format` в CI |

У каждого гейта есть **негативный тест**: если сломать вход, скрипт обязан упасть. Иначе «зелёно»
ничего не доказывает.

## 8. Как выглядит типичный цикл на практике

1. Вы приносите материалы заказчика → их разбирает **аналитик**, отвечает на вопрос «зачем и как
   измерим успех».
2. **Архитектор** пишет предложение. Вы читаете и ставите `Status: Approved`.
3. **Разработчик** реализует по `tasks.md`, отмечая чекбоксы.
4. **QA** независимо прогоняет проверки и заполняет `acceptance.md`.
5. **Ревьюер** смотрит двумя осями: стандарты и спецификация. `Fail` → возврат разработчику.
6. **Ops** пишет changelog, версию, план отката.
7. **Оркестратор** архивирует: дельты уходят в `specs/`, предложение — в `archive/`.

По дороге нерешённое не теряется: оно становится `OQ-N` в
[`OPEN_QUESTIONS.md`](../OPEN_QUESTIONS.md), а ответ на него — записью `D-NNN`
в [`DECISIONS.md`](../DECISIONS.md).

## 9. Три вещи, которые стоит запомнить

1. **Spec First.** Пока нет утверждённой спецификации — кода не будет. Это не бюрократия:
   именно здесь отсекаются «сделал не то».
2. **Один источник на правило.** Команды — в `config.yaml`, фазы — в конституции, стандарты —
   в `openspec/standards/`. Если два документа противоречат — это дефект, а не «нюанс».
3. **Человек владеет решениями, агент — исполнением.** Утверждение спецификации, юридические и
   продуктовые вопросы, коммиты и релизы — за вами. Модель лишь требует, чтобы каждое решение было
   зафиксировано и проверяемо.
