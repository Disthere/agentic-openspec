# Объективная оценка набора SDD (`agentic-openspec`)

**Дата:** 2026-11-11 · **Предмет:** шаблон SDD + мультиагентной разработки для C#/.NET
**Среда:** DeepSeek Harness 0.2.2-rc.1 · **Владелец:** .NET-разработчик
**Метод:** полное чтение репозитория (126 файлов, 96 в `HEAD`, ~895 КБ, ~8900 строк текста, **0 строк C#**),
машинные прогоны проверок, сверка с внешними практиками (Spec Kit 1.3.3, OpenSpec 1.17.0, Kiro, agentskills.io,
официальная документация DSH), проверка живого DSH-профиля через `--dump-config`.

> **Важно об изменениях:** структура и содержимое файлов набора **не менялись**. Единственный созданный файл —
> этот отчёт. Временный `DSH_HOME` для проверки `install.ps1` создавался вне репозитория и удалён.

## 1. Итоговый вердикт

Набор — **сильная работа с правильной архитектурой идеи и системным дефектом реализации**. Оценка по осям:

| Ось | Оценка | Одна фраза |
| - | - | - |
| Архитектура процесса SDD | **8/10** | Конституция, гейты, фазы с владельцами и артефактами — продумано лучше, чем у большинства публичных шаблонов |
| Реализация «канона правил» | **3/10** | Канон заявлен, но детализация живёт в зеркале, которое среда не читает; 7–10 копий почти каждого правила |
| Машинная проверяемость гейтов | **3/10** | Все 6 гейтов декларативны; исполняемого валидатора нет, CI не подключён, схемы противоречат фактам |
| Готовность шаблона к раздаче | **3/10** | 34% объёма — история разработки самого набора; журнал одной машины вшит в точку входа агента |
| Адаптация к существующему проекту | **8/10** | `docs/legacy/` + «код = факт» + проверка «ответ за один переход» — главная уникальная ценность набора |
| .NET-фундамент | **5/10** | Настройки грамотные (CPM, анализаторы, deterministic — проверено), но в заявленной конфигурации **не собирается**: net8.0 против net10.0-only пакетов, `dotnet new xunit` ломается о CPM, проектов нет вовсе |
| Обвязка DeepSeek Harness | **2/10** | Профиль **композируется** (проверено, exit 0), но **роли не работают**: у всех 6 пресетов `plugins:` = только `persona` → нет инструментов, нет `AGENTS.md`, нет скиллов; делегирование с `agentPreset` не сконфигурировано |
| Гигиена (лицензии, ссылки, консистентность) | **3/10** | Производные без атрибуции, MIT-заголовок уезжает в продукты пользователя, 3 версии формата архива |

**Одной фразой:** это профессионально спроектированный процесс, который **не имеет ни одного работающего
автоматического гейта**, **не собирается в заявленной конфигурации .NET**, **не исполняется в DSH**
(шесть ролей — описания персон без инструментов) и на 34% состоит из истории собственной разработки,
включая личный журнал сессии в файле, который читает каждый агент при каждом старте.

**Что это значит практически.** Три независимых контура процесса — .NET-гейт, spec-гейт, ролевая модель
в DSH — **ни один не был исполнен хотя бы один раз**. Все шесть предложений (`001`…`006`) помечены `Approved`,
ни одно не `Done`, `openspec/specs/` пуст, `archive/` пуст: **цикл SDD ни разу не был замкнут на себе**.
В логах 12 сессий рабочего пространства `agentPreset` = `standard` во всех 12 — ни одного прогона роли.
Это не три разных дефекта, а один: набор писался, но не прогонялся. Даже единственный документированный
«живой прогон ревьюера» в `006/acceptance.md:104` — это прогон `standard`, а не пресета `reviewer`.

**Отдельно про .NET-часть — самый острый вывод.** Три P0 (нет проектов; `net8.0` против
net10.0-only пакетов; `dotnet new xunit` против CPM) означают, что **.NET-фундамент набора ни разу не был
скомпилирован**. Настройки при этом написаны грамотно и по современным практикам (CPM с транзитивным пином,
`AnalysisLevel=latest-recommended`, `Deterministic`, `UseArtifactsOutput` — проверено через `msbuild -getProperty`).
Дефект не в качестве замысла, а в отсутствии прогона.

**Отдельно про DSH-часть — самый неожиданный вывод.** Семантика патч-слоя понята верно и проверена
(`override` vs `insert`, `--dump-config` exit 0 — это реальная победа предложения `003`), но проверка
остановилась на «дерево собралось». Функциональность роли — инструменты, инструкции, скиллы — не проверялась,
и её нет. То есть `003` закрыл дефект загрузки и не заметил дефекта содержания.

### Исправленная ошибка первой редакции этого отчёта

В первой редакции я утверждал, что правило «никогда `== null`» **ловится сборкой**, ссылаясь на
`.editorconfig:82` (`dotnet_style_prefer_is_null_check_over_reference_equality_method = true:warning`).
**Это неверно, и я это проверил по первоисточнику.** Правило IDE0041 (Microsoft Learn, «Use 'is null' check»)
применяется к `Object.ReferenceEquals(value, null)` и `(object)o == null` — то есть к *приведению к object*
и к вызову `ReferenceEquals`, а **не** к обычному `x == null`. Meziantou-анализаторы MA0141/MA0142, которые
делают ровно это (`x != null` → `is not null`, `x == null` → `is null`), в `.editorconfig` **не включены**
(там всего 4 записи `dotnet_diagnostic.` — проверено). Значит стандарт `01-code-style.md:111` обещает
механику, которой нет. Это находка **P2-19** ниже. Спасибо аудитору, который поймал это на ревью.

### Исправленный вывод первой редакции: «профиль работает» — только наполовину

В первой редакции я записал в сильные стороны: «`dsh\install.ps1` → **Успех**: профиль разворачивается,
`--dump-config` композируется, 10 пресетов». Это верно ровно в той части, которую проверяет `--dump-config`:
**дерево композируется без ошибок**. Это не то же самое, что «роли работают», и я проверил разницу:

```
$ dsh --profile agentic-openspec --dump-config   # exit 0, 1428 строк, 10 пресетов — да
```

но в извлечённом дереве у каждого из шести наших пресетов секция `plugins:` содержит **ровно один** элемент:

| Пресет набора | Плагины в композиции |
| - | - |
| `preset-analyst` … `preset-ops-release` (все 6) | только `@deepseek-ai/dsh-persona` |
| `preset-standard` (штатный) | `persona`, `agent-instructions`, `time-context`, `tool-bash`, `tool-pwsh`, `tool-fs`, `tool-fs-search`, `tool-jobs`, `tool-schedule`, `skill-filesystem`, `tool-skill`, `command-goal`, `tool-goal`, `planning`, `plan-mode`, `compaction`, `tool-result-pruner`, `delegation`, `tool-subagent`, `tool-subagent-fork`, `workflow-ptc` |

А host-строки инструментов в web-профиле **погашены** (`disabled: true` — проверено в дампе на строках
183–311: `tool-bash`, `tool-pwsh`, `tool-fs`, `skill-filesystem`, `tool-subagent`, `agent-instructions`
и т.д.). То есть в Web-профиле инструменты живут **только внутри пресета**.

**Вывод: роль, запущенная с нашим пресетом, не получает ни `read/write/edit`, ни `pwsh`, ни `skill`,
ни подгрузки `AGENTS.md`.** Значит шесть ролей набора — не работающая обвязка, а **корректно
скомпонованное описание персон без исполнительной части**. Это находка **P0-1** ниже, и она —
самая тяжёлая во всём аудите.

**Подтверждено и то, что роли ни разу не запускались:** в логах 12 сессий рабочего пространства
(`~/.dsh/sessions/--C-Projects-agentic-openspec--/`) во всех 12 `agentPreset` = `standard`.
Ни одного прогона `analyst`/`architect`/`csharp-dev`/`qa-engineer`/`reviewer`/`ops-release`.

## 3. Сильные стороны (что сделано лучше, чем у большинства)

**1. Конституция как настоящий высший приоритет, а не декорация.**`openspec/constitution.md:3-4` объявляет приоритет, и он реально применяется: `006/proposal.md:44-47`
ссылается на §5 при оформлении исключений, `12-desktop.md:11` — на §5 для выхода за периметр.
Правило «нет артефакта — нет гейта» (`constitution.md:80-81`) — редкое и правильное: гейт должен быть
подтверждаем документом, иначе это лозунг.

**2. Фазы жизненного цикла с тройной привязкой «артефакт → гейт → владелец».**
`constitution.md:66-76` — 9 фаз, у каждой артефакт, гейт и владелец. Плюс `config.yaml:90-100` дублирует
это машиночитаемо. Это уровень зрелости, которого нет ни у Spec Kit, ни у OpenSpec из коробки.

**3. Правило допуска роли: «роль без артефакта и гейта не добавляется»** (`constitution.md:86-87`).
Защищает от типичной болезни мультиагентных наборов — десяти персон, которые ничего не решают.

**4. Двухосевое ревью с раздельными отчётами и запретом «победителя».**
`.agents/reviewer.md:18-20` и `.agents/skills/code-review/SKILL.md:17-19` объясняют *зачем* две оси
(маскировка одной оси другой) — это совпадает с практикой Google eng-practices и cc-sdd.
Свежая сессия на ось, read-only, устойчивые ID находок, диспозиции `fixed/rejected/deferred`, правило трёх
циклов (`references/findings.md`) — сильная часть набора.

**5. Дисциплина «улики вместо заявлений» с честной фиксацией невыполненного.**
`CHANGELOG.md:152-166` перечисляет, что `dotnet build`/`test` **не** запускались; `006/acceptance.md:5`
— «на реальном проекте не выполнялось»; `001/acceptance.md:47` — «в `src/` ещё нет кода; предмета ревью не было».
Шаблоны почти никогда так не делают. Это прямо усиливает доверие к остальным утверждениям набора.

**6. Профильная модель как ось конфигурации** (`config.yaml:15-29`, `schemas/README.md:15-22`).
Один проект = один профиль; профиль определяет схему + набор стандартов + разделы DoD. Это чистое
решение, которого нет у конкурентов, и оно масштабируется на третий-четвёртый профиль.

**7. Контур ретрофита существующего проекта — уникальная ценность.**
`docs/legacy/` (реестр `LEG-NNN`, карта «их документ → наш артефакт», «источник истины один»,
«ничего не удаляется»), правило «код = факт» (`04-documentation.md:228-231`, `D-013`), и главное —
**измеримая проверка** «ответ за один переход» с фиксированными 10 вопросами и таблицей Pass/Fail
(`ADOPTION.md:601-636`). Именно этого нет ни у OpenSpec, ни у Spec Kit, и именно это решает вашу реальную боль.

**8. Семантика патч-слоя DSH понята верно — это подтверждённая победа предложения `003`.**
`dsh/profile/cordis.patch.yml:4-13` документирует `override` для существующих id против `insert` для новых;
проверено: `install.ps1` → exit 0, затем `--dump-config` → exit 0, ровно один `agent-preset-registry`,
10 пресетов. Реальная ошибка (`patch: entry "preset-analyst" not found`) была найдена и исправлена,
с матрицей приёмки (`003/acceptance.md:11-20`). Это правильный инженерный цикл: нашли — починили — записали улику.

**9. `install.ps1` действительно работает в Windows PowerShell 5.1** и не ломается на кириллице:
pure-ASCII комментарий (`:4-5`), проверка источника (`:13`), fallback `$DSH_HOME` (`:9`), подсказки по CLI
(`:24-36`). Проверено в чистом `$DSH_HOME` — exit 0. (Остаётся P1-16: затирает файл без бэкапа.)

**10. Документация места скиллов точна на уровне констант** — редкий случай.
`dsh/README.md:110-118` (ранги 100/200/300/400/500, `project-agents = <root>/.agents/skills`, маркер корня `.git`,
`<name>/SKILL.md`, обязательные `name`/`description`) совпадает с реализацией
`dsh-skill-filesystem/lib/index.js:20-24,160-197,678-718`. Обычно такие таблицы в документации врут;
здесь — нет.

**11. Централизованное управление версиями и анализаторами — на уровне dotnet/eShop.**
`Directory.Packages.props` с `ManagePackageVersionsCentrally` + `CentralPackageTransitivePinningEnabled`,
`Directory.Build.props` с `AnalysisLevel=latest-recommended`, `EnforceCodeStyleInBuild`, `Deterministic`,
`UseArtifactsOutput`, `ContinuousIntegrationBuild` под `CI=true`. **Проверено запуском** — применяется к проектам.
SonarAnalyzer и Meziantou подключены как `PrivateAssets="all"` — правильно.

**12. Лицензионная дисциплина — с одним исключением (P1-8).**
`Directory.Packages.props:22-23`: FluentAssertions запинен на `7.2.2` (последняя Apache-2.0) с **явным комментарием**
о платной 8.x, и это подтверждено nuspec на nuget.org. Для шаблона, который копируют в коммерческие проекты,
это редкая и правильная аккуратность. (Проблема лишь в том, что защита держится комментарием, а не правилом.)

**13. Сквозная непереиспользуемая нумерация в четырёх реестрах** (`IN-NNN`, `OQ-N`, `D-NNN`, `LEG-NNN`)
с явными правилами. Даёт адресуемый след «требование → решение → версия».

**14. Машиночитаемый каркас профилей** (`openspec/schemas/*.yaml` с `required_sections` и грамматикой
`requirement`/`scenario`, реестр `IN-NNN`, разделы DoD по фазам) — набор **можно** проверять автоматически;
не хватает только исполнителя, а не модели проверки.

**15. Явный список того, что делает только человек** (`ADOPTION.md:517-532`) с правилом «если делаете
не из списка — это ошибка процесса». Даёт пользователю инструмент обнаружения превышения полномочий агентом.

**16. Цельный `.editorconfig` из традиции dotnet/runtime** с осознанными приглушениями и обоснованиями:
`IDE0055:warning` (формат ломает сборку), `CA2007 = none` с объяснением про отсутствие SynchronizationContext
в ASP.NET Core (`:172-177`). Приглушения документированы, а не молчаливы.

## 4. Семь системных выводов

**СВ-1. Работает форма процесса, а не контроль над ним.**
Каждый из шести гейтов (`constitution.md:21-29`) — декларация. `dotnet build/test/format` в корне падает
с `MSB1003`; схемы не исполняются ничем (единственные скрипты в репозитории — `ai_tells_check.py`,
относящийся к другому скиллу, и `dsh/install.ps1`); workflow лежит в `docs/ci/`, а `.github/workflows/` пуст;
`config.yaml:69` объявляет активную схему `spec-first`, файла которой не существует.
**Все «Pass по схеме» в шести `acceptance.md` — ручной пересказ, а не результат проверки.**
Скрипт на ~150 строк + подключённый workflow закрывают 4 из 6 гейтов.

**СВ-2. Цикл не замкнут, потому что у шага Archive нет владельца.**

**СВ-3. Канон расщеплён на пять описаний одного процесса — и зеркало оказалось полнее канона.**
`AGENTS.md` — 59 строк / 6 КБ. `.clinerules` — 182 строки / 16,8 КБ, и именно там живут: запрет `== null`,

который среда игнорирует. При этом `.clinerules:4` говорит «Оркестратор — главная сессия DSH», а
`.clinerules:100` — «**Cline** выступает Оркестратором». Плюс третье описание в `openspec/README.md:29-33`
(6 шагов), четвёртое в `constitution.md` (9 фаз), пятое в `config.yaml:workflow` + `lifecycle`.

**СВ-4. Цена процесса превысила объём задачи, а шаблон превратился в свалку собственной истории.**
0 строк C# при 895 КБ текста и 6 предложениях **о самом процессе**. `006` — 70 КБ описания процедуры,

журнал уже устарел (заявляет 118 файлов — фактически 126).

**СВ-5. Единственная часть, спроектированная как конфигурация, — профили. Остальное спроектировано как текст.**
Профильная модель работает. Всё остальное — правила, гейты, фазы, роли — существует в виде прозы в 7–10 копиях,
которую синхронизирует человек. Набору нужен **один машинный источник истины для собственных правил**,
а не больше текста.

**СВ-6. Настройки написаны правильно, но ни разу не были исполнены — и это самый дорогой дефект.**
Шесть P0 — не ошибки незнания, а следствие отсутствия прогона. .NET: `net8.0` против net10.0-only пакетов
(P0-6), `dotnet new xunit` против CPM (P0-7), ноль проектов (P0-8) — каждая обнаруживается **первым** же
`dotnet restore` в чистом каталоге. DSH: пресеты без инструментов (P0-9), несконфигурированное делегирование
(P0-10), ложная загрузка `AGENTS.md`/скиллов у ролей (P0-11) — каждая обнаруживается **первым** же запросом
«перечисли доступные инструменты» в сессии роли. Общий принцип набора — «измеряй, не заявляй»
(`constitution.md:11`) — не применён к самому набору ни в одной из трёх частей.

**СВ-7. «Дерево собралось» трижды было принято за «работает» — и это один и тот же дефект мышления.**
`--dump-config` exit 0 + «six presets present» записано как доказательство в `dsh/README.md:55-62` и
`SESSION-START.md:23-24`. Но `--dump-config` проверяет **композицию**, а не **функциональность**: пресет
без инструментов композируется без единой ошибки. Точно так же `acceptance.md` фиксирует «Pass по схеме»
без исполнения схемы (СВ-1) и «гейт зелёный» без запуска сборки. Набор трижды принял **наличие артефакта
за выполненность гейта** — это тот же паттерн, что породил незамкнутый цикл (СВ-2) и «Pass» в acceptance
при `Not run` в ревью. Если у этого аудита есть один главный вывод — он здесь: набору нужен не новый
документ, а привычка прогонять то, что объявлено проверенным.

только persona. **Проверять не `--dump-config`, а реальным запросом «перечисли доступные инструменты»

**P0-11. Заявление «DSH читает `AGENTS.md`» верно для штатных пресетов и неверно для шести ролей;

### Где индустрия разошлась (и что это значит для набора)

1. **«Спека как контракт» vs «спека как второй код».** Замеренная цена: обзор markdown дороже обзора кода,
   харнесс даёт ×7 стоимости без выигрыша на сильной модели (Thoughtworks, 2026-10). Вывод для вас:
   процесс оправдан на нетривиальных изменениях и **неоправдан** на мелочах — нужен лёгкий маршрут (пункт 11).
2. **Гейты фаз vs fluid-итерация.** OpenSpec строит позиционирование на «no rigid phase gates»; Spec Kit —
   на явных гейтах. Набор выбрал гейты — это осознанно и для вашего профиля (high-load, микросервисы,
   контракты) правильно. Но гейт без машинной проверки — это ритуал, а не гейт.
3. **Один AGENTS.md vs тонкие адаптеры.** Доминирующий паттерн — «один канонический файл + адаптер-импорт»
   (Claude Code `@AGENTS.md`, Cursor читает `.agents/skills`, DSH читает и `AGENTS.md`, и `CLAUDE.md`
   с дедупом по содержимому). Набор выбрал «канон + зеркало-пересказ» — самый дорогой и хрупкий вариант (P0-2).
4. **Скиллы как место правды vs клиентские инструкции.** OpenSpec официально: «prefer skills, expect to retire
   commands». Набор движется в эту сторону правильно (4 скилла, `.agents/skills` подхватывается DSH автоматически).
5. **Насколько жёстко валидировать спеку.** OpenSpec — единственный из большой четвёрки, кто валидирует
   структуру машинно. Это ближайший образец: `openspec validate --strict`, лимиты на размер требования,
   отдельный режим `--archived` для «все чекбоксы закрыты».

## 10. Ограничения этой оценки

- **Не проверял живьём:** прогон шести ролей с **исправленной** композицией (её пока нет — это задача 1.10),
  нагрузочный контур (`performance.md`), работоспособность `csharp-desktop`-стека (Avalonia/LLamaSharp/ONNX),
  точный триггер перезаписи патча профиля приложением (P1-16 фиксирует факт дрейфа и риск, но не момент записи).
- **Не юридическая консультация:** по P1-12 (производные скиллы) нужен человек; я фиксирую факты
  (`license: null` у источника, отсутствие `NOTICE`, MIT vs CC BY-SA), а не квалификацию.
- **Оценка «преждевременности» десктоп-профиля — суждение**, зависит от того, стартует ли продукт
  под него в ближайшие недели.
- `dotnet restore`/`build`/`test` в этом окружении недоступны (сетевая ошибка доступа к nuget.org),
  поэтому версии пакетов сверены по API nuget.org, применение `Directory.Build.props` — через
  `msbuild -getProperty` (работает без restore), а поведение `dotnet new xunit` — фактической генерацией
  в временном каталоге.
- **Уверенность по P0-9 (пресеты без инструментов) высокая, но не 100%:** вывод следует из композиции
  (`registry` монтирует только `config.plugins`, host-строки `tool-*` в web-профиле `disabled: true`)
  и подтверждён дампом. Живьём я не поднимал сессию с пресетом роли; это и есть задача 1.12.
  Как проверить за минуту: сессия с пресетом `analyst` → «перечисли доступные инструменты».

## 12. Оценка достоверности этого отчёта

Отчёт собирался из пяти независимых источников: моих собственных машинных проверок, аудита
`openspec/`-процесса, аудита документации/дублирования, аудита .NET-фундамента и аудита слоя
«агенты и среда» (с извлечением реализации DSH из `app.asar`). Ключевые утверждения перепроверены
первоисточниками (nuget.org, dotnet/core `releases-index.json`, Microsoft Learn, GitHub API,
сборка DSH и дампы `--dump-config`, `dotnet new`, ref-сборки BCL, логи сессий) — минимум по одному
независимому свидетельству на находку P0/P1.

**В первой редакции этого отчёта было два собственных дефекта**, найденных на ревью и исправленных:

1. **Ошибка** (§2): утверждение, что запрет `== null` ловится сборкой. Проверено по Microsoft Learn —
   IDE0041 покрывает только `ReferenceEquals`/`(object)x == null`.
2. **Неполнота** (§2, новый блок): вывод «профиль работает» был сделан по `--dump-config` exit 0, что
   проверяет композицию, но не функциональность. Живая проверка показала: у всех 6 пресетов ролей
   `plugins:` = только `persona` (P0-9).

Второй дефект — методический, и он же оказался главной находкой всего аудита (СВ-7): я повторил ровно ту
ошибку, которую вменял набору — принял «дерево собралось» за «работает». Фиксирую это явно, потому что
аудит, который сам является частью SDD-набора, обязан подчиняться принципу «измеряй, не заявляй».

**Где оценка остаётся суждением, а не фактом:** «преждевременность» desktop-профиля; необходимость лёгкого
маршрута (следует из практики индустрии, а не из измерения вашего рабочего процесса); юридическая
квалификация P1-12 (нужен человек).

**Что проверено живьём в DSH:** `install.ps1` в чистом `$DSH_HOME`, `--dump-config` (exit 0, 1428 строк),
полная композиция 6 наших пресетов (только `persona`), `disabled: true` на host-строках инструментов,
отсутствие `allowedAgentPresets`, реальный список шаблонов профилей (`acp|headless|sdk|sdk-minimal|web`),
дрейф установленного профиля против репозиторного, 12 сессий рабочего пространства (все `agentPreset: standard`),
падение `ai_tells_check.py` на этой машине и заглушка `python` (exit 9009).
