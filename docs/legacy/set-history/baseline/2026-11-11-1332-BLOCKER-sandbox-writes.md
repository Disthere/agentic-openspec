# Блокер: дочерние процессы не могли писать в подкаталоги воркспейса

**Зафиксировано:** 2026-11-11 13:32–14:20 (+05:00) при выполнении Батча 0
**Статус: РЕШЁН** · причина установлена, устранена, проверена. Батчи 1–5 разблокированы.

## Симптом (был)

Под политикой `workspace-write` дочерний процесс (`pwsh`, `cmd.exe`, `[IO.File]`, а значит
`dotnet`, `git`) не мог создать, изменить или удалить файл в любом **существующем** подкаталоге
репозитория:

```
New-Item : Отказано в доступе по пути "baseline".
[IO.File]::WriteAllText("…\docs\_w1.tmp")  -> UnauthorizedAccessException (0x80070005)
cmd /c "echo x > …\docs\_c.txt"            -> Access is denied.
```

Работало при этом: запись в корень, создание нового каталога в корне, запись в новый каталог,
и чтение где угодно. Инструменты `write`/`edit` харнесса тоже писали нормально — ограничение сидело
именно на дочерних процессах.

## Корневая причина (установлена и доказана)

**Несовпадение обязательных меток целостности (Mandatory Integrity Label).**

Дочерний процесс песочницы работает на **низком** уровне целостности:

```
whoami /all  ->  Обязательная метка\Низкий обязательный уровень  S-1-16-4096
```

Правило Windows: процесс с низким IL **не может писать** в объект, чья метка отсутствует или выше.
Объект без явной метки трактуется как Medium. Было:

| Объект | Метка Low IL | Запись дочерним процессом |
| - | - | - |
| корень воркспейса | **есть** `(OI)(CI)(NW)` | OK |
| новый каталог в корне | **есть** (унаследована) | OK |
| `%TEMP%\dsh-…` | **есть** | OK |
| `docs`, `openspec`, `src`, `tests`, `.agents`, `.github`, `dsh`, `inputs`, `.git`, файлы в корне | **НЕТ** | **DENIED** |

Разница между рабочим и нерабочим объектом — ровно наличие метки Low. DACL при этом был в порядке:
у `docs` после ремонта стоял явный `FullControl` для пользователя, и запись всё равно отклонялась —
потому что проверка целостности выполняется **до** проверки прав и её не видно в `icacls` по умолчанию.

Все затронутые каталоги проверены: не reparse-точки, `Directory`, владелец — текущий пользователь,
`AreAccessRulesProtected=False`.

## Почему штатный ACL-скрипт не помог

Запускался `diagnose-windows-sandbox-acl` (`-Path docs -AllowRoot . -Out …-acl-report`).
Он выдал `GRANTED` + `verified` — и это правда: он починил `WRITE_DAC`/`WRITE_OWNER`. Но лечит он
**DACL**, а блокер был в **метке целостности** (SACL-подобный атрибут), которую скрипт не трогает.
`nextAction=verify_original_confined_operation` корректно указал, что дальше нужно проверить
исходную операцию — она и показала, что причина другая.

## Что сделано

Для каждого каталога и файла воркспейса:

1. выдан явный `FullControl` текущему пользователю (без него нельзя менять метку — нужен WRITE_OWNER);
2. проставлена та же метка, что уже стояла у корня:

```powershell
icacls C:\Projects\agentic-openspec /setintegritylevel (OI)(CI)low /T /C
```

Итог финального прохода: `Successfully processed 919 files; Failed processing 0 files`.

## Единственный побочный эффект

Все файлы воркспейса теперь имеют явную метку Low IL. Для обычной работы это не мешает:
процессы Medium IL (ваш терминал, IDE, `git` из обычной консоли) **могут** писать в объекты Low —
ограничение действует только в обратную сторону. Если понадобится вернуть как было:

```powershell
# снять метку у дерева (вернуть наследование/Medium):
icacls C:\Projects\agentic-openspec /setintegritylevel (OI)(CI)medium /T /C
```

## NU1301 — та же причина, а не сеть

Важное уточнение. `NU1301` первоначально выглядел как сетевая проблема, но измерения показали,
что **это то же ограничение Low IL**:

| Условие | TLS-рукопожатие к `api.nuget.org` | `dotnet restore` |
| - | - | - |
| дочерний процесс, **Low IL** (песочница) | `No credentials are available in the security package` | **NU1301** |
| процесс на **Medium IL** (расширенный режим) | **OK**, TLS 1.3 | **exit 0** |
| процесс на Medium IL: `Invoke-WebRequest` | **HTTP 200** | — |

Причина: Schannel (поставщик TLS в Windows) не может получить доступ к хранилищу ключей/сертификатов
из процесса с низким уровнем целостности, поэтому рукопожатие обрывается ещё до сети. TCP-соединение
при этом устанавливается успешно — что и сбило с толку при первом диагнозе.

**Практическое следствие:** `nuget.org` доступен, пакеты восстанавливаются. Батч 1 выполним.
`dotnet restore` и `dotnet build` проходят (`xunit.v3.templates` устанавливается, шаблон `xunit3`
доступен). Оговорка: снять закэшированными пакетами не всё (`xunit.v3`, `nsubstitute` отсутствуют в
локальном кэше), поэтому restore требует сети — а сеть есть, но только вне песочницы.

## Побочный эффект устранения

Все файлы воркспейса получили явную метку Low IL. Обычной работе это не мешает: процессы Medium IL
(ваш терминал, IDE, `git` из обычной консоли) **могут** писать в объекты Low — ограничение действует
только в обратную сторону. Если понадобится вернуть как было:

```powershell
icacls C:\Projects\agentic-openspec /setintegritylevel (OI)(CI)medium /T /C
```

**Остаётся ограничение:** восстановление NuGet-пакетов и любой TLS из дочерних процессов под
`workspace-write` недоступны (ограничение хранилища ключей Windows, §5 конституции тут ни при чём).
Для шагов вида `dotnet restore` нужен запуск с расширенным доступом либо переключение сессии в
full access на время батча.
