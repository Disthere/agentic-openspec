# Как развернуть и использовать SDD-набор

Инструкция для человека. **Интерфейс — только промпты.** Команд в терминале вы не набираете, файлы
руками не правите, конфиги не сводите. Единственное ручное действие с файлами — **развернуть набор**
(см. ниже), и позже — скопировать папку с материалами заказчика.

> Если в промпте есть уголки `<...>` — замените на своё значение. Остальное копируйте целиком, одним
> блоком, как есть.

## 0.1 Как развернуть набор: одна модель развёртывания (решение D-019)

**Основной путь — GitHub «Use this template»** (репозиторий помечен `is_template`). Он создаёт
чистую копию без истории набора, с уже сброшенными реестрами.

**Копирование папки — офлайн-режим** (нет доступа к GitHub). Результат тот же, но историю набора
придётся убрать самостоятельно — пройдите [`docs/CLEANUP.md`](./CLEANUP.md) (10 минут).

Что копируется и что нет:

| Путь | Use this template | Копирование папки |
| - | - | - |
| `AGENTS.md`, `.clinerules`, `openspec/`, `.agents/`, `tools/` | да | да |
| `src/`, `tests/` (smoke-пара) | да | да |
| `LICENSE` | **замените своей** | **замените своей** |
| `THIRD-PARTY.md` | да, **сохраните** | да, **сохраните** |
| `docs/legacy/set-history/`, `docs/baseline/`, `docs/session/` | нет (не входит) | **удалите** |

> `LICENSE` не должна уезжать в продукт: набор — шаблон, а не ваш проект. Обязательства перед
> сторонними материалами при этом сохраняются в `THIRD-PARTY.md`.

## 0. Что делает человек, а что — сессия

| Действие | Кто | Как часто |
| - | - | - |
| Установить DeepSeek Harness и профиль `agentic-openspec` | вы (по [инструкции профиля](../dsh/README.md)) | один раз на машину |
| **Скопировать одну папку — корень набора** `agentic-openspec` — в проект | вы | один раз на проект |
| Скопировать папку с материалами в `inputs/` | вы | по мере появления материалов |
| Отправлять промпты и отвечать на уточняющие вопросы | вы | всегда |
| Нажимать «Разрешить» / «Approve» в DSH, когда сессия просит | вы | всегда |
| Утверждать спецификацию (`Approved`) | вы — словами в чат; правку делает агент | один раз на предложение |
| Ключи, сертификаты, оплата, юридические решения | только вы | по необходимости |
| Разбор материалов, спецификации, код по спецификации, тесты, улики, ревью, changelog, подготовка релиза | сессия DSH с ролями | — |

**Чего вы не делаете:** не набираете команды, не редактируете документы и конфиги, не решаете, какой файл
куда положить, не сводите конфликтующие настройки, не заполняете чек-листы. Это работа сессии; ваша —
решения и разрешения.

### Кому адресованы промпты

**Все промпты — в главную сессию (Оркестратор).** Переключать пресеты вручную не нужно: разделение работы
уже прописано внутри каждого промпта, а главная сессия сама запускает нужные роли и собирает результат.

| Шаг | Куда отправляете промпт | Кто выполняет работу | Что появляется на выходе |
| - | - | - | - |
| Промпт 0 | главная сессия | она же | отчёт готовности, без правок |
| A2 | главная сессия | она же | набор, приведённый под продукт |
| A3 | главная сессия → роль `analyst` | продуктовый аналитик | `inputs/INDEX.md`, `OPEN_QUESTIONS.md`, Discovery gate |
| A4 | главная сессия → роль `architect` | архитектор | папка предложения (Draft) |
| A5 | главная сессия | она же | `Status: Approved`, запись в `DECISIONS.md` |
| B1 | главная сессия | она же (перенос и слияние) | набор, встроенный в существующий проект |
| B1a | главная сессия → роль `architect` | архитектор (только чтение) | реестр `docs/legacy/INDEX.md` со статусами `⏳` и правила `docs/legacy/README.md` |
| B2 | главная сессия → роль `architect` | архитектор | baseline-предложение «как есть» |
| B3 | главная сессия | она же | оценка применимости стандартов |
| B5 | главная сессия → роль `architect` | архитектор | документы-указатели, маркеры архива и внешних документов, разобранный чужой changelog, `OQ-N` по расхождениям |
| B6 | главная сессия (по желанию — через роль `reviewer`, только чтение) | она же; `reviewer` даёт «слепой» проход | таблица Pass/Fail «ответ за один переход» с числом переходов |
| Ц1 | главная сессия → `analyst` (если нужен) → `architect` | аналитик, затем архитектор | предложение (Draft) |
| Ц2 | главная сессия | она же | утверждение и запись решения |
| Ц3 | главная сессия → `csharp-dev`, затем `qa-engineer` | разработчик, инженер верификации | код, тесты, `acceptance.md`, `performance.md` |
| Ц4 | главная сессия → `reviewer` | ревьюер (только чтение) | вердикт и находки; агрегирует Оркестратор |
| Ц5 | главная сессия → `ops-release` | Ops/Release | changelog, версия, план отката, документы |
| Ц6 | главная сессия | она же | архив предложения и обновлённые `specs/` |

**Почему не «пишите прямо роли»:**

- агрегация остаётся в одном месте: блокирующая находка по любой оси даёт `Fail`, повторный проход
  назначает Оркестратор (см. [`.agents/reviewer.md`](../.agents/reviewer.md));
- сохраняется трассировка «требование → задача → улика → вердикт» — улики и вердикт не теряются между
  сессиями;
- роль без своего гейта не имеет смысла: гейт закрывает Оркестратор, а не отдельный исполнитель.

**Две оговорки:**

- **Ревьюера** можно запустить и напрямую — новая сессия с пресетом `sdd` и промптом «Ты — Ревьюер»,
  если нужен «слепой» проход без контекста автора. Но вердикт всё равно принесите в главную сессию:
  она ведёт `acceptance.md`, `CHANGELOG.md` и назначает исправления.
- Если главная сессия начала писать код без утверждённой спецификации — значит в сессии выбран пресет
  `sdd` (у него SDD-персона, но роль задаётся промптом). Дефолт реестра — нейтральный `standard`
  (решение `D-018`, закрыл `OQ-13`). В начале **каждого** промпта уже есть строка «Ты — Оркестратор SDD
  этого проекта»; если этого не хватает, усильте её явным запретом («код пишет только роль `csharp-dev`
  по утверждённой спецификации»).

## 1. Перед стартом

1. DSH Desktop установлен; профиль `agentic-openspec` установлен — в нём шесть ролей (аналитик, архитектор,
   разработчик, инженер верификации, ревьюер, Ops/Release).
2. Провайдер моделей настроен: ключ вводится **в приложении** (Settings → Models) или задаётся переменной
   окружения. В репозиторий ключи не попадают никогда.
3. Папка набора есть на диске, например `C:\path\to\agentic-openspec`.

Сессию лучше открывать в **корне проекта** (рабочее пространство = корень репозитория).

**Промпт 0. Проверка готовности**

```text
Ты — Оркестратор SDD этого проекта.
Проверь готовность к работе по SDD в этом проекте и выведи короткий отчёт:
— доступен ли профиль agentic-openspec и шесть ролей-пресетов (analyst, architect, csharp-dev,
  qa-engineer, reviewer, ops-release);
— виден ли набор: AGENTS.md, openspec/, .agents/, docs/;
— какой профиль проекта активен сейчас и соответствует ли ему схема валидации.
Если чего-то не хватает — скажи, что именно мне сделать руками (например, установить профиль),
и больше ничего не меняй.
```

## 2. Сценарий A — новый проект с нуля

### Шаг A1. Копирование (руками, один раз)

**Что копировать:** папку **`agentic-openspec`** — это весь репозиторий набора целиком, тот каталог,
в котором лежат `AGENTS.md`, `.agents/`, `openspec/`, `docs/`, `dsh/`, `inputs/`, `README.md` и файлы сборки.
Не отдельные файлы и не вложенные каталоги — именно эту папку.

Скопируйте её туда, где будет проект, и переименуйте в имя продукта (например, `Capsul-A`).
Это всё, что вы делаете руками с файлами на старте.

**Откуда взять папку** — любой удобный способ без командной строки:

| Способ | Что получите |
| - | - |
| GitHub → **Code → Download ZIP** → распаковать | папка `agentic-openspec-main` — переименуйте в имя продукта |
| Локальная копия набора на диске | папка набора — но удалять/чистить в ней ничего не нужно, см. ниже |

**Что попадёт в копию** (это нормально — так и задумано):

| Внутри | Зачем |
| - | - |
| `AGENTS.md`, `.clinerules`, `.github/` | правила для агента и указатели инструментов |
| `.agents/` | шесть ролей и скиллы |
| `openspec/` | конституция, стандарты, схемы, шаблоны предложений, живые спецификации |
| `docs/` | архитектура, эксплуатация, шаблоны, эта инструкция |
| `dsh/` | профиль среды (ставится один раз на машину) |
| `inputs/` | пустые каталоги под материалы заказчика + реестр |
| `README.md`, `CHANGELOG.md`, `OPEN_QUESTIONS.md`, `DECISIONS.md`, `LICENSE` | служебные документы проекта |
| `global.json`, `Directory.Build.props`, `Directory.Packages.props`, `.editorconfig`, `.gitignore` | настройки сборки и стиля |
| `src/`, `tests/` | пустые заготовки под исходники и тесты |

**Что могло попасть лишнее** — про это отдельно позаботится сессия на шаге A2, вам делать ничего не нужно:

- служебная папка `.git`, если копировали локальную копию (в ZIP её нет): в промпте A2 сессия удалит её
  и инициализирует репозиторий продукта, чтобы проект не оказался привязан к репозиторию набора;
- демонстрационные заглушки и примеры — их сессия тоже убирает на A2.


### Шаг A2. Инициализация проекта

**Промпт A2. Инициализируй проект из набора**

```text
Ты — Оркестратор SDD в этом репозитории. Разверни набор под проект.

Сначала уточни у меня (по одному вопросу, не более пяти):
— название и суть продукта одной фразой;
— профиль проекта: csharp-api (сервер, ASP.NET Core) или csharp-desktop (десктоп, локальные модели);
— целевая платформа и главные сценарии пользователя;
— имя владельца продукта для документов.

Затем сделай:
0) если в корне есть служебная папка `.git` от набора — удали её и инициализируй репозиторий продукта
   (первый коммит делать не нужно), чтобы проект не оказался привязан к репозиторию набора;
1) прочитай AGENTS.md, openspec/constitution.md, openspec/config.yaml, openspec/standards/README.md;
2) приведи под проект README.md, AGENTS.md (карту репозитория), openspec/project.md, docs/SESSION-START.md;
3) выставь активный профиль в openspec/config.yaml и подтверди, что схема валидации и набор стандартов
   соответствуют этому профилю;
4) запиши решение о профиле в DECISIONS.md по формату файла;
5) убери демонстрационные заглушки набора и файлы примеров, оставив шаблоны (000-*);
6) проверь целостность: обязательные файлы на месте, ссылки в картах резолвятся;
7) добавь запись в CHANGELOG.md под [Unreleased] с привязкой к этой инициализации.

Верни краткий отчёт: что изменил, какие вопросы остались и в какую папку мне положить материалы
заказчика. Кода не пиши, существующие файлы проекта не трогай.
```

### Шаг A3. Материалы заказчика

Скопируйте папку с материалами (ТЗ, концепции, макеты, образцы данных) **внутрь** `inputs/` — одной
операцией копирования.

**Промпт A3. Разбери материалы и закрой Discovery**

```text
Ты — Оркестратор SDD этого проекта.
Делегируй субагенту analyst: разбери всё, что появилось в inputs/ (включая вложенные папки),
и выполни фазу Discovery.
Нужно: зарегистрировать каждый материал в inputs/INDEX.md с IN-NNN и статусом; сформулировать проблему,
пользователей, ценность и ИЗМЕРИМЫЙ критерий успеха первого релиза; вынести всё нерешённое
в OPEN_QUESTIONS.md (OQ-N) с рекомендуемым значением по умолчанию; отметить противоречия между материалами.
Спецификации и код не писать. Верни отчёт: список IN-NNN, критерий успеха, вопросы ко мне,
состояние Discovery gate (закрыт или нет) и что именно требуется от меня.
```

Если гейт не закрыт — просто ответьте на вопросы в чате, агент сам обновит `OPEN_QUESTIONS.md` и повторит.

### Шаг A4. Первая спецификация

**Промпт A4. Подготовь предложение первого релиза**

```text
Ты — Оркестратор SDD этого проекта.
Делегируй субагенту architect: на основе закрытого Discovery создай предложение
openspec/proposals/<первый-свободный-номер>-<короткое-имя-релиза>/ со всеми артефактами: proposal.md, tasks.md,
acceptance.md, specs/<capability>/spec.md и, при необходимости, design.md, contracts/, performance.md.
Статус — Draft.

Требования — пронумерованные, каждое с проверяемым сценарием; у каждой задачи — трассировка к требованию.
Объём: одно обозримое изменение (не более пятнадцати задач), остальное — следующими предложениями.
Код не писать.

Верни отчёт: путь к предложению, список возможностей, открытые вопросы и однострочную рекомендацию —
утверждать или нужны уточнения.
```

### Шаг A5. Утверждение — ваше решение

Прочитайте предложение: это тот единственный момент, где вы обязаны вникнуть. Затем отправьте:

**Промпт A5. Утверждаю спецификацию**

```text
Ты — Оркестратор SDD этого проекта.
Утверждаю предложение 001. Поставь Status: Approved, зафиксируй решение в DECISIONS.md, закрой
открытые вопросы, которые я подтвердил выше, и перечисли, что именно теперь согласовано.
Дальше действуй по циклу изменения — docs/ADOPTION.md, раздел 4.
```

## 3. Сценарий B — существующий проект, где SDD не использовали

Ничего не пересоздавайте и не переносите репозиторий: набор встраивается в текущий проект и **не трогает
продукт** — только добавляет процесс вокруг него.

### Если у проекта уже есть своя документация

Свои ADR, ТЗ, `docs/` с другой иерархией, собственный `CHANGELOG.md`, исторические документы и wiki /
Confluence / Google Docs вне репозитория — эта инструкция **покрывает** их шагами ниже. Порядок сценария B
становится таким: B1 (набор встроен) → **B1a** (инвентаризация и карта, только чтение) → B2 (baseline по
коду) → B3 (применимость стандартов) → B4 (первое изменение) → **B5** (приведение документации по
утверждённым строкам) → **B6** (проверка «ответ за один переход», раздел 7).

**Что покрыто:**

- **реестр документов** `docs/legacy/` — `README.md` с правилами и шаблонами, `INDEX.md` с записями
  `LEG-NNN`: где документ живёт (путь или URL), владелец, потребитель, актуальность, наш артефакт;
- **карта соответствий** «их документ → наш артефакт»: у каждой строки реестра есть наш артефакт либо явное
  «нет соответствия» и ровно одно действие;
- **указатели и маркеры статусов** (`⏳ не разобран`, `➡ указатель`, `🗄 архив`, `🌐 внешний`, `❓ вопрос`,
  `❌ отклонён`): перенесённое оставляет документ-указатель без нормативного текста, поэтому одно поведение
  описано в одном месте;
- **чужой `CHANGELOG.md`** — анализируется: актуальные записи переносятся в проектный `CHANGELOG.md`
  как датированная история с указанием источника, остальное уходит приложением
  `docs/legacy/CHANGELOG-FROZEN.md` за одной строкой-указателем; ничего не теряется;
- **внешние документы** (wiki, Confluence, Google Docs) — указатель в реестре; выгружается только то, что
  задаёт поведение или решение, а секреты и персональные данные не копируются никогда;
- **расхождения «документ vs код»** — код считается фактическим поведением, документ помечается устаревшим
  или замещаемым, расхождение выносится в `OPEN_QUESTIONS.md` как `OQ-N` с рекомендуемым дефолтом;
- **проверка «ответ за один переход»** — фиксированный список вопросов и таблица Pass/Fail с числом
  переходов (промпт B6 в разделе 7).

**Что остаётся за вами:** утвердить строки реестра словами «утверждаю LEG-NNN» — до этого шаг B5 не
начинается; удаление любого чужого документа — отдельное решение владельца, процедура ничего не удаляет.
Ручных файловых операций она не добавляет: реестр создаёт сессия, вы только утверждаете.

Подвопросы темы вынесены в [`OPEN_QUESTIONS.md`](../OPEN_QUESTIONS.md) как `OQ-15`…`OQ-20`: место реестра,
внешняя документация, судьба оригиналов после переноса, чужой `CHANGELOG.md`, «код = факт», машинная
проверка реестра.

### Шаг B1. Копирование (руками, один раз)

Скопируйте папку набора **внутрь корня существующего репозитория**. Она нужна как источник: дальше сессия
разложит её содержимое по правильным местам и удалит копию. Служебную папку `.git` внутри набора переносить
не нужно (в ZIP её нет) — если она там оказалась, сессия удалит её сама.

**Промпт B1. Разверни набор в этом проекте**

```text
Ты — Оркестратор SDD этого проекта.
В корне репозитория лежит папка с нашим SDD-набором (<ИМЯ ПАПКИ>). Встрой её в этот проект.

Сначала разведка — ничего не менять: определи стек, структуру решения, где исходники и тесты, есть ли уже
AGENTS.md, .clinerules, .editorconfig, Directory.Build.props, Directory.Packages.props, global.json, README.
```

## 4. Цикл изменения — как менять проект дальше

Любое изменение проходит один путь: **Explore → Propose → Approve → Apply → Verify → Review → Release → Archive**.
Промпты идут по порядку; между ними вы только отвечаете и утверждаете. Все промпты отправляйте **в главную
сессию** — она вызывает роли согласно таблице в §0 и собирает результат.

**Промпт Ц1. Разберись и предложи** (разведка + спецификация)

```text
Ты — Оркестратор SDD этого проекта.
Задача: <одна-две фразы о том, что нужно изменить>.
Делегируй субагенту analyst, если нужны материалы или уточнения, затем субагенту architect:
исследуй живые спецификации (openspec/specs/) и код, после чего создай предложение
openspec/proposals/<следующий номер>-<короткое-имя>/ со всеми артефактами, статус — Draft.

В требованиях обязательно: как изменение влияет на существующее поведение и совместимость,
и что в объём НЕ входит. Объём — не более пятнадцати задач.

Код не писать. Верни отчёт: путь к предложению, требования, риски, открытые вопросы и рекомендацию —
утверждать или нужны уточнения.
```

**Промпт Ц2. Утверждаю**

```text
Ты — Оркестратор SDD этого проекта.
Утверждаю предложение <номер>. Поставь Status: Approved, зафиксируй решение в DECISIONS.md,
закрой открытые вопросы, которые я подтвердил, перечисли согласованное и переходи к реализации.
```

**Промпт Ц3. Реализуй и собери улики** (реализация + верификация)

```text
Ты — Оркестратор SDD этого проекта.
Делегируй субагенту csharp-dev: реализуй ровно задачи из tasks.md предложения <номер>, отмечая их
выполнение, и прогони гейт верификации активного профиля (сборка, тесты, формат, архитектурные тесты).
Ничего сверх спецификации.

Затем делегируй субагенту qa-engineer: заполни acceptance.md уликами — строка на каждое требование,
непроверенное вынеси отдельно с причиной и планом; performance.md — если изменение влияет на ресурсы,
скорость или размер поставки.

Верни отчёт: статус, затронутые файлы, результаты проверок, отклонения от спецификации.
```

**Промпт Ц4. Независимое ревью**

```text
Ты — Оркестратор SDD этого проекта.
Делегируй субагенту reviewer: проведи ревью изменения <номер> по скиллу code-review — две независимые
оси, Standards (стандарты активного профиля) и Spec (требования и поведение), один агрегированный вердикт,
находки с идентификаторами, уликами и диспозициями.

Код, тесты и спецификации не правь. Если вердикт Fail — перечисли, что должен сделать разработчик,
и не исправляй сам.
```

**Промпт Ц5. Подготовь релиз**

```text
Ты — Оркестратор SDD этого проекта.
Делегируй субагенту ops-release: подготовь релиз изменения <номер> — запись в CHANGELOG.md по формату
проекта, версию по SemVer, план отката и обновление эксплуатационных документов. Для десктопного профиля
дополнительно: установщик, подпись, офлайн-режим и лицензионный инвентарь.

Проверь релизный гейт по разделу DoD активного профиля и верни отчёт: что готово, что блокирует выпуск
и что требуется от меня.
```

**Промпт Ц6. Архивируй**

```text
Ты — Оркестратор SDD этого проекта.
Изменение <номер> принято. Перенеси предложение в openspec/proposals/archive/<дата>-<номер>-<имя>/,
влей его дельты в openspec/specs/, обнови карты репозитория, убедись, что ссылки резолвятся.
Верни короткий отчёт: что перенесено и что изменилось в живых спецификациях.
```

| Шаг | Что делает сессия | Что появляется в репозитории | Что нужно от вас |
| - | - | - | - |
| Ц1 | разведка, требования, дизайн, задачи | папка предложения | ответы на уточняющие вопросы |
| Ц2 | фиксирует решение | `Status: Approved`, запись в `DECISIONS.md` | решение «утверждаю» |
| Ц3 | код по спецификации + улики | код, тесты, `acceptance.md`, `performance.md` | разрешения и разбор спорных мест |
| Ц4 | независимое ревью | вердикт и находки | решение по блокирующим находкам |
| Ц5 | релизная подготовка | changelog, версия, план отката, документы | сертификаты, даты, ключи |
| Ц6 | архивация | `proposals/archive/`, обновлённые `specs/` | ничего |

## 7. Как понять, что развёртывание удалось

**Промпт «Проверь развёртывание»**

```text
Ты — Оркестратор SDD этого проекта.
Проверь, что развёртывание SDD в этом проекте завершено, и выдай чек-лист с результатами Pass или Fail:
— AGENTS.md, .clinerules и .agents/ на месте; роли описаны, скиллы видны сессии;
— openspec/ на месте: конституция, config.yaml, standards, schemas, proposals, specs, шаблоны 000-*;
— активный профиль выбран, схема валидации и набор стандартов ему соответствуют;
— docs/SESSION-START.md, CHANGELOG.md, DECISIONS.md, OPEN_QUESTIONS.md, inputs/INDEX.md заполнены по проекту;
— ссылки в картах репозитория резолвятся;
— пробный черновик предложения проходит самопроверку по схеме активного профиля (создай и удали его).
Для каждого пункта — Pass или Fail и что именно исправить. Ничего не исправляй без моей команды.
```

**Промпт B6. Ответ за один переход**

Отдельная проверка документации — после шага B5 и как повторяемая проверка после крупных переносов. Она
показывает не «кажется, стало понятно», а таблицу: на каждый вопрос новый участник находит ответ за один
переход или нет.

```text
Ты — Оркестратор SDD этого проекта.
Проверь, что новый участник находит ответ по документации за один переход от точек входа
(README.md, AGENTS.md, docs/legacy/INDEX.md). Ничего не исправляй — только проверяй.

Задай по репозиторию ровно эти десять вопросов и для каждого покажи путь до ответа:
1) что это за продукт и для кого;
2) как его собрать и запустить;
3) какую версию сейчас эксплуатируем и что в ней изменилось;
4) какие у продукта публичные контракты;
5) какие архитектурные решения приняты и почему;
6) где описаны SLO, ёмкость и runbook;
7) какие требования заказчика действуют и где они зарегистрированы;
8) какие вопросы открыты и какие решения приняты;
9) какие стандарты обязательны и где исключения;
10) как внести изменение по процессу (от идеи до релиза).

Правила подсчёта: переход — это ссылка, по которой надо пройти, чтобы получить ответ.
Ответ из точки входа — 0 переходов; из документа, на который точка входа ссылается напрямую, —
1 переход. Ответ, найденный только поиском или только в памяти агента, — Fail.
Для каждого вопроса: Pass (≤ 1 перехода) или Fail (> 1 перехода либо ответа нет), число переходов,
путь и что мешает.

Отдельно проверь машинно:
— все ссылки в docs/legacy/INDEX.md резолвятся;
— у каждой строки реестра есть наш артефакт либо явное действие;
— архивные документы помечены, документы-указатели соответствуют шаблону и не содержат правил.

Верни таблицу «вопрос → Pass/Fail → переходы → путь» и одну строку итога. Ничего не правь.
```

## 8. Почему это работает

- **Spec First**: сначала спецификация в `openspec/proposals/`, потом код; исключений нет
  ([`constitution.md`](../openspec/constitution.md)).
- **Фазы с гейтами**: у каждой фазы есть артефакт, гейт и владелец — от разбора материалов до поддержки
  ([`constitution.md`](../openspec/constitution.md) §7).
- **Независимость**: улики собирает не автор кода, вердикт выносит отдельная роль
  ([`.agents/README.md`](../.agents/README.md)).
- **Улики вместо обещаний**: приёмка — матрица «требование → проверка → результат» с явно отмеченным
  непроверенным ([`standards/05-definition-of-done.md`](../openspec/standards/05-definition-of-done.md)).
