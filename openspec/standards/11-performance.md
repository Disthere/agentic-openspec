# 11. Производительность и нагрузка

Ключевой принцип: **измеряй, не заявляй.** Утверждение «оптимизировано»/«выдержит нагрузку» без воспроизводимого
замера, описанного окружения и сравнения — **недействительно**. Основано на методике
[dotnet/aspnetcore `docs/Benchmarks.md`](https://github.com/dotnet/aspnetcore/blob/main/docs/Benchmarks.md) (Crank).

## 11.1 Что требуется для performance-изменения

Артефакт `performance.md` в предложении (шаблон — [`../../openspec/proposals/000-performance.md`](../../openspec/proposals/000-performance.md)):

- **Профиль запросов**: сценарии, доли RPS между ними, размеры полезной нагрузки, доля чтения/записи.
- **Целевые показатели**: throughput (RPS), p95/p99 latency, допустимый процент ошибок.
- **Ресурсы и длительность**: CPU/RAM/инстансы, длительность теста, прогрев.
- **Окружение измерений**: версии SDK/runtime, ОС/железо, конфигурация сервиса и зависимостей.

## 11.2 Методика (Crank-совместимая)

1. Выбрать **сценарий** (как в Benchmarks ASP.NET Core: plaintext/json/fortunes/... или собственный endpoint).
2. **Зафиксировать окружение и версии** — прогон должен быть детерминированным и воспроизводимым.
3. Снять **baseline** (до изменения) и **candidate** (после), сравнить одну и ту же метрику.
4. Приложить команду прогона и конфигурацию к `performance.md`, чтобы результат можно было повторить.
5. Регресс латентности/throughput без объяснения = `Fail` на ревью.

```console
# Crank — локальный/удалённый прогон (пример)
dotnet tool install Microsoft.Crank.Controller --version "0.2.0-*" --global
crank --config <scenario>.yml --scenario <name> --profile <local|aspnet-...>
```

> Официальная инфраструктура perf lab доступна только членам команды .NET — для проекта используйте
> собственное окружение измерений, но сохраняйте ту же дисциплину (сценарий + окружение + сравнение).

## 11.3 Правила

- Никаких SLO-заявлений без нагрузочного теста в описанном окружении.
- Горячие пути — без лишних аллокаций и LINQ (см. [`01-code-style.md`](./01-code-style.md)); ссылки/буферы — пулы.
- Изменения пулов, таймаутов, параллелизма обосновываются замером.
- Наблюдаемые показатели теста фиксируются в [`10-observability.md`](./10-observability.md) (метрики p95/p99, ошибки, saturation).

## 11.4 Критерии приёмки производительности

- [ ] Сценарий воспроизводим (команда + конфигурация приложены).
- [ ] Окружение и версии описаны.
- [ ] Есть сравнение baseline vs candidate по целевым метрикам.
- [ ] Целевые p95/p99/throughput/ошибки достигнуты.
- [ ] Регрессы отсутствуют либо объяснены и согласованы.
