# 03. Handoffs (передача контекста)

Handoff — формализованная передача контекста между этапами, сервисами или людьми. У каждого handoff есть
**вход**, **выход** и **критерии приёмки**.

## 3.1 Типы handoffs

| Handoff | Откуда | Куда | Артефакт | Критерии приёмки |
| - | - | - | - | - |
| **Spec → Code** | Спецификация | Разработка | Контрактный код (генерация), ручная логика | Компилируется, тесты проходят, есть трассируемость |
| **Code → Test** | Код | Тестирование | Тест-кейсы, BDD-сценарии | Покрытие ≥80% (Domain ≥90%), граничные случаи покрыты |
| **Dev → Dev** | Разработчик | Разработчик | PR (описание + спека + тесты) | CI зелёный, ревью пройдено, документация обновлена |
| **Service → Prod** | Разработка | Прод | Образ контейнера, конфиг, миграции, Helm/k8s-манифесты | Smoke-тесты пройдены, health-checks зелёные, мониторинг настроен, есть rollback |
| **Service → Service** | Сервис A | Сервис B | Контракт (`.proto` / OpenAPI / схема сообщения) | Контракт задокументирован, версионирован, покрыт consumer-driven contract-тестами |

## 3.2 Формат handoff-документа

Для каждого handoff создаётся документ (или секция в PR):

```markdown
# Handoff: Spec → Code (PAY-001)

## Контекст
Реализация создания платежа согласно спеке PAY-001.

## Входные артефакты
- `openspec/specs/payments/spec.md#create-payment`
- `specs/contracts/payments.proto`

## Выходные артефакты
- `src/Payments.Application/CreatePaymentHandler.cs`
- `src/Payments.Api/Endpoints/CreatePaymentEndpoint.cs`
- `tests/Payments.UnitTests/CreatePaymentHandlerTests.cs`

## Критерии приёмки
- [ ] Код компилируется без warnings
- [ ] Все тесты проходят
- [ ] Покрытие >80% (Domain >90%)
- [ ] Трассируемость (spec-id в XML-док)
- [ ] Ревью пройдено

## Известные ограничения
- Не поддерживает частичный возврат (будет в PAY-002)
```

## 3.3 Handoffs в CI/CD

Автоматизируем handoffs через пайплайны:

```yaml
# .github/workflows/spec-to-code.yml
name: Spec to Code Handoff
on:
  push:
    paths:
      - 'specs/contracts/**.proto'

jobs:
  generate:
    steps:
      - name: Generate C# from Protobuf
        run: dotnet tool run protobuf-gen --input specs/contracts --output src/Generated

      - name: Validate generated code
        run: dotnet build src/Generated -c Release

      - name: Run contract tests
        run: dotnet test tests/Contracts.IntegrationTests -c Release

      - name: Create PR with generated code
        run: gh pr create --title "Auto-generated from spec" --body "..."
```

## 3.4 Правила handoff

- Ни один handoff не пропускает **гейт верификации** (`dotnet build` + `dotnet test`).
- Изменение контракта между сервисами — только через **новый handoff Service → Service** с версионированием.
- Каждый handoff линкуется: предложение → спека → код → тесты. Разрыв трассируемости = `Fail` на ревью.

## 3.5 Handoff наружу (внешний исполнитель / подрядчик)

Передача работ за периметр: другой команде, подрядчику, внешнему вендору. От внутренних handoff'ов
отличается **фильтрацией** — наружу уходит только необходимое, и ничего лишнего.

**Принципы:**

1. **Контракт — единственная точка соприкосновения.** Подрядчик реализует к контракту и внутрь сервиса не заходит.
2. **Объективная приёмка.** Не «нравится / не нравится», а тесты, contract-тесты и DoD-чеклист из пакета.
3. **Пакет версионируется.** Изменение контракта = новая версия пакета и период совместимости
   (см. [конституцию](../constitution.md), раздел 4).
4. **Один пакет — одна зона ответственности.** Не «весь проект», а ограниченный объём работ.
5. **Обратимость.** Контракт и тесты позволяют заменить исполнителя без переписывания (bus factor).
6. **Секреты не покидают периметр.** Песочница, мок или ограниченный аккаунт с ротацией
   ([`09-security.md`](./09-security.md)).

**Состав пакета** — `handoff/<NNN-slug>-vX.Y/`:

| Файл | Что внутри |
| - | - |
| `MANIFEST.md` | Версия, дата, ID предложения, вехи, состав, **что исключено и почему**, контакты |
| `spec.md` | Требования и сценарии (`WHEN`/`THEN`) в терминах исполнителя |
| `contracts/` | OpenAPI / `*.proto` / схемы событий: версия, совместимость, семантика ошибок |
| `deliverables.md` | Что и в каком виде сдаётся (артефакты, формат, куда размещается) |
| `acceptance.md` | Как будет проверяться: команды, тесты, contract-тесты, границы |
| `env.md` | Версии SDK/рантайма, сборка и запуск, песочница |
| `standards/` | Только применимый срез (например `01-code-style.md`, `06-api.md`, `05-definition-of-done.md`) |

**Что НЕ уходит наружу** (проверяется чек-листом):

- `inputs/` целиком — материалы заказчика могут быть конфиденциальными (только явные выдержки);
- `DECISIONS.md`, `OPEN_QUESTIONS.md`, внутренние ADR (в т.ч. «почему решили не так»);
- `.clinerules`, `.agents/`, `dsh/` — наши процессы и обвязка;
- история предложений, чужие сервисы, инфраструктура, секреты и строки подключения.

**Процесс:**

1. Спецификация утверждена; часть работ выделена наружу.
2. **Архитектор** собирает пакет по [`docs/HANDOFF-TEMPLATE.md`](../../docs/HANDOFF-TEMPLATE.md) — он владеет контрактом.
3. **Ревьюер** проходит чек-лист «что утекает» и подтверждает состав; секреты или лишнее — `Fail`.
4. Передача с фиксацией версии пакета; обратно приходит артефакт и прогон тестов против контракта.
5. Приёмка: contract-тесты, DoD, при необходимости нагрузочные; результат — запись в `CHANGELOG.md`.
