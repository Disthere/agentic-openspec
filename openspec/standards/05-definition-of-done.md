# 05. Definition of Done (DoD)

DoD — обязательный чек-лист приёмки. **Ревьюер** использует его как основу вердикта `Pass`/`Fail`.

## 5.1 DoD для спецификации

- [ ] Спецификация написана в Markdown.
- [ ] Есть диаграммы (Mermaid/PlantUML), где это помогает.
- [ ] Спецификация прошла ревью (минимум 2 ревьюера).
- [ ] Спецификация связана с бизнес-требованиями.
- [ ] Есть примеры (input/output) и граничные случаи.
- [ ] Каждое требование имеет ≥1 проверяемый сценарий (`WHEN`/`THEN`).
- [ ] Открытые вопросы вынесены в [`OPEN_QUESTIONS.md`](../../OPEN_QUESTIONS.md) (либо явно зафиксировано «открытых нет»).

## 5.2 DoD для кода

- [ ] Код соответствует Code Style (проверено линтерами, [`01-code-style.md`](./01-code-style.md)).
- [ ] Все тесты проходят (unit, integration).
- [ ] **FluentAssertions ≤ 7.2.2** — 8.x **запрещён** (Xceed, платная лицензия). Проверка версии:
      `dotnet list package` не должен показывать `FluentAssertions` ≥ 8.0.0; альтернатива без смены
      API — `AwesomeAssertions`. Моки — `NSubstitute`; **Moq не используется** (в CPM его нет).
- [ ] Покрытие > 80% (для Domain > 90%).
- [ ] Нет warnings от анализаторов (NetAnalyzers, Sonar, Meziantou).
- [ ] XML Doc Comments для публичных API + трассируемость (`spec-id`).
- [ ] Нет sync-over-async, нет `.Result`/`.Wait()`, нет проглоченных исключений.
- [ ] Внешние вызовы: таймауты, retry/circuit breaker (Polly), `CancellationToken`.
- [ ] Горячие пути без лишних аллокаций и без LINQ.
- [ ] Улики проверок (`acceptance.md`, `performance.md`) добыты не автором кода — Инженером верификации
      ([`.agents/qa-engineer.md`](../../.agents/qa-engineer.md)); непроверенное отмечено явно.
- [ ] Код прошёл ревью (минимум 1 ревьюер).
- [ ] CI зелёный.

## 5.3 DoD для сервиса / шаблона (Scaffold)

- [ ] Сервис/шаблон собирается и запускается (`dotnet build`, `dotnet run`).
- [ ] Есть README с инструкцией по запуску и конфигурации.
- [ ] Есть примеры сгенерированного кода / контрактов.
- [ ] Health-checks (`/health/live`, `/health/ready`) отвечают.
- [ ] Настроена наблюдаемость (OpenTelemetry: traces/metrics/logs).
- [ ] Есть Dockerfile и базовые k8s-манифесты.
- [ ] Шаблон протестирован (генерация + сборка + тесты).
- [ ] Документация (README, ADR) обновлена.

## 5.4 DoD для релиза

- [ ] Все фичи реализованы и протестированы.
- [ ] Документация обновлена (спеки, ADR, runbook).
- [ ] Changelog написан ([шаблон](../../docs/CHANGELOG-TEMPLATE.md); формат Keep a Changelog + привязка к задачам).
- [ ] Решения по закрытым вопросам зафиксированы в [`DECISIONS.md`](../../DECISIONS.md); открытых вопросов, влияющих на поведение, нет.
- [ ] Smoke-тесты пройдены.
- [ ] Мониторинг и алерты настроены (SLO/ошибки/latency).
- [ ] Миграции БД проверены (обратимость, backfill).
- [ ] Runbook обновлён.
- [ ] Откат возможен (rollback plan: `kubectl rollout undo` / feature flags).

## 5.8 DoD для десктоп-продукта (профиль `csharp-desktop`)

Заменяет 5.3 и 5.4 для десктопного профиля ([`12-desktop.md`](./12-desktop.md)). Владелец фазы —
Ops / Release ([`.agents/ops-release.md`](../../.agents/ops-release.md)).

- [ ] Установщик ([Velopack](./12-desktop.md) / Inno Setup) ставит приложение **без прав администратора**; деинсталляция чистая.
- [ ] Артефакты подписаны; при установке проверяется подпись.
- [ ] Обновление: подписанный манифест проверен, дельта-пакет применён, документирован **возврат на предыдущую версию**.
- [ ] Офлайн-режим: основные сценарии работают при отключённой сети.
- [ ] Бюджеты ресурсов измерены на эталонном железе и записаны (`performance.md`); UI не блокируется во время инференса.
- [ ] Доказуемость приватности: архитектурные тесты (NetArchTest + анализатор запрета сети) зелёные, сценарий «нулевой egress» зафиксирован в `acceptance.md`.
- [ ] Телеметрии нет: в зависимостях отсутствуют SDK аналитики, в сценарии нет сетевых вызовов.
- [ ] Лицензионный инвентарь (`licenses.md`) заполнен: компоненты, версии, лицензии, обязательства; **нет GPL/AGPL и NC**.
- [ ] Модели: лицензия каждой зафиксирована в манифесте; файлы моделей в репозитории отсутствуют.
- [ ] Changelog для пользователя написан человекочитаемо; техническая запись — в `CHANGELOG.md` с привязкой `(<ID>)`.

## 5.5 Как это применяется в SDD

- **Архитектор** отмечает в `proposal.md` → `## Test Strategy` и `## Impact`, какие пункты DoD затрагиваются.
- **Разработчик** не сдаёт работу, пока не выполнены 5.2 и применимые пункты 5.3.
- **Продуктовый аналитик** закрывает дискавери (5.6) до начала спецификации: без зарегистрированного
  входа и измеримого критерия успеха задача не уходит Архитектору.
- **Инженер верификации** добывает улики (5.2) и закрывает Verification gate; автор кода не подтверждает
  собственную работу.
- **Ops / Release** закрывает 5.4 и 5.7: релиз без записи в changelog, плана отката и runbook не считается
  готовым.
- **Ревьюер** выполняет двухосевой проход по скиллу [`code-review`](../../.agents/skills/code-review/SKILL.md)
  (ось Standards — стандарты и DoD, ось Spec — требования и поведение), ведёт находки с устойчивыми ID и
  диспозициями и возвращает `Fail` со ссылкой на конкретный непройденный пункт DoD
  (например, «5.2: покрытие Domain 78% < 90%»).
- **Оркестратор** агрегирует результат: блокирующая находка по любой оси — `Fail`; запахи кода и стилевые
  наблюдения не блокируют. Фича не объявляется завершённой, пока DoD релиза (5.4) не выполнен.

## 5.6 DoD для дискавери (Discovery)

Владелец фазы — Продуктовый аналитик ([`.agents/analyst.md`](../../.agents/analyst.md)); гейт — Discovery
(карта фаз — [`constitution.md`](../constitution.md) §7).

- [ ] Каждый использованный материал заказчика зарегистрирован в [`inputs/INDEX.md`](../../inputs/INDEX.md) (`IN-NNN`) и имеет актуальный статус.
- [ ] Проблема и ценность сформулированы: для кого и какую проблему решаем.
- [ ] Критерий успеха измерим: метрика, текущее значение, целевое значение, способ замера.
- [ ] Макеты и концепции (`graphics/`, `concepts/`) либо учтены, либо явно помечены как не подлежащие реализации.
- [ ] Все нерешённые вопросы вынесены в [`OPEN_QUESTIONS.md`](../../OPEN_QUESTIONS.md) с рекомендуемым дефолтом.
- [ ] Намётки капабилити переданы Архитектору; требований «из воздуха» нет.

## 5.7 DoD для эксплуатации и поддержки (Operate)

Владелец фазы — Ops / Release ([`.agents/ops-release.md`](../../.agents/ops-release.md)); гейты — Release
(5.4) и Support.

- [ ] SLO и SLI описаны в [`docs/operations/slo.md`](../../docs/operations/slo.md); алерты настроены на их нарушение.
- [ ] Ёмкость и лимиты зафиксированы в [`docs/operations/capacity.md`](../../docs/operations/capacity.md).
- [ ] Runbook сервиса существует и проверен: симптомы, шаги разбора, эскалация, откат.
- [ ] Health-checks (`/health/live`, `/health/ready`) отвечают в целевом окружении.
- [ ] Обратная связь описана: канал приёма обращений, кто разбирает, что считается инцидентом.
- [ ] Инциденты и запросы поддержки заведены как `OQ-N` или предложение — не оставлены в переписке.
- [ ] Пост-релизный разбор проведён: сигналы, срок наблюдения, что сделано с находками.
- [ ] Эксплуатационные документы обновлены по факту изменения.
