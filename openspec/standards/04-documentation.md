# 04. Документация артефактов

Документация — часть артефакта, а не отдельная сущность. Код без документации считается незавершённым.

## 4.1 Уровни документации

| Уровень | Что документируем | Формат | Где хранится |
| - | - | - | - |
| **Spec** | Бизнес-правила, архитектура | Markdown, Mermaid | `openspec/` |
| **API** | Публичные интерфейсы, методы | XML Doc Comments | В коде (`///`) |
| **Code** | Сложная логика, решения | Комментарии в коде | В коде (`//`) |
| **Runbook** | Запуск, настройка, диагностика | Markdown | `docs/operations/runbooks/` |
| **ADR** | Архитектурные решения | Markdown (шаблон) | `docs/architecture/adr/` |
| **Changelog** | Что изменилось между релизами | Markdown (Keep a Changelog) | `CHANGELOG.md` (корень) |
| **Open Questions** | Нерешённые вопросы и ответы пользователя | Markdown (таблица `OQ-N`) | `OPEN_QUESTIONS.md` (корень) |
| **Decisions** | Журнал принятых решений | Markdown (записи `D-NNN`) | `DECISIONS.md` (корень) |
| **Input** | ТЗ, концепции, макеты, материалы заказчика | Любой (pdf/docx/png/csv…) | `inputs/` (корень) |
| **Handoff (наружу)** | Пакет работ для внешнего исполнителя | Markdown + контракты | `handoff/<NNN-slug>-vX.Y/` |
| **Legacy** | Документация, существовавшая до SDD: реестр, карта соответствий | Markdown | `docs/legacy/` |

## 4.2 Шаблон XML Doc Comments

```csharp
/// <summary>
/// Создаёт новый платёж и публикует событие PaymentCreated.
/// </summary>
/// <param name="command">Данные платежа (сумма, валюта, получатель).</param>
/// <param name="ct">Токен отмены.</param>
/// <returns>Идентификатор созданного платежа.</returns>
/// <exception cref="ArgumentNullException">Если <paramref name="command"/> is null.</exception>
/// <exception cref="ArgumentOutOfRangeException">Если сумма ≤ 0.</exception>
/// <spec-id>PAY-001</spec-id>
/// <example>
/// <code>
/// var id = await handler.CreateAsync(new CreatePayment(Money.Of(100m, "USD")), ct);
/// </code>
/// </example>
/// <remarks>
/// Идемпотентно по <c>Idempotency-Key</c>: повторный вызов с тем же ключом возвращает тот же результат.
/// </remarks>
public Task<PaymentId> CreateAsync(CreatePayment command, CancellationToken ct) { /* ... */ }
```

## 4.3 Шаблон ADR (Architecture Decision Record)

```markdown
# ADR-001: gRPC/Protobuf для внутренних контрактов

## Статус
Accepted

## Контекст
Нужно передавать данные между микросервисами с минимальной задержкой и строгой типизацией.

## Решение
Используем gRPC + Protobuf для внутренних контрактов между сервисами.

## Альтернативы
- REST + JSON: проще, но медленнее и менее строгий контракт
- MessagePack: компактнее, но слабее экосистема контрактов
- GraphQL: гибкий, но избыточный для inter-service вызовов

## Последствия
- ✅ Строгая типизация и генерация кода
- ✅ Высокая производительность (HTTP/2, бинарная сериализация)
- ✅ Версионирование через package/эволюцию полей
- ❌ Нужен protoc/`Grpc.Tools`
- ❌ Менее читаемо «в сыром виде»
```

## 4.4 Шаблон Runbook (микросервис)

```markdown
# Runbook: сервис payments-api

## Предварительные требования
- .NET 8 SDK, Docker, доступ к кластеру k8s
- Секреты/строки подключения — из конфигурации окружения (не из репозитория)

## Деплой
1. Собрать образ: `docker build -t payments-api:$(git rev-parse --short HEAD) .`
2. Применить манифесты: `kubectl apply -f deploy/`
3. Проверить rollout: `kubectl rollout status deploy/payments-api`

## Диагностика
### Проблема: сервис не становится Ready
**Симптом:** `/health/ready` возвращает 503
**Решение:** проверить зависимости (БД, брокер), логи `kubectl logs deploy/payments-api`

### Проблема: рост latency запросов
**Симптом:** p99 > SLO в трейсах OpenTelemetry
**Решение:** проверить пул соединений, медленные запросы (EF Core логи), троттлинг внешних вызовов

## Масштабирование и откат
- Горизонтально: `kubectl scale deploy/payments-api --replicas=N` (сервис stateless)
- Откат: `kubectl rollout undo deploy/payments-api`
```

## 4.5 Правила

- Публичные API **обязаны** иметь XML Doc Comments (иначе — warning от анализатора).
- Каждое архитектурное решение — ADR со статусом (`Proposed`/`Accepted`/`Superseded`).
- Каждый сервис — Runbook (деплой, диагностика, откат, масштабирование).
- Документация обновляется в том же PR, что и код.

## 4.6 Changelog

Формат — [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версионирование — [SemVer](https://semver.org/lang/ru/).
Файл — `CHANGELOG.md` в корне проекта. Готовый к копированию шаблон — [`docs/CHANGELOG-TEMPLATE.md`](../../docs/CHANGELOG-TEMPLATE.md).

**Правила:**

- Заголовок записи — `## [X.Y.Z] — YYYY-MM-DD · <суть в одну строку> (<ID>)`, где `(<ID>)` — **привязка к задаче**:
  ID предложения (`openspec/proposals/<NNN-slug>`), `spec-id` (`PAY-001`) или issue (`#123`). Без привязки запись не принимается.
- Версия по SemVer: **MAJOR** — ломающее изменение, **MINOR** — новая функциональность, **PATCH** — исправление.
- Незавершённое накапливается в `## [Unreleased]` и при релизе переносится в `## [X.Y.Z] — YYYY-MM-DD`.
- Секции (пишутся только непустые). Стандартные: `Добавлено`, `Изменено`, `Исправлено`, `Удалено`, `Устарело`, `Безопасность`.
  Наши дополнения: `Не изменилось` (явно: дефолтное поведение прежнее), `Производительность` (замер baseline→candidate),
  `Миграция` (для ломающих изменений), `Тесты` (число тестов и предупреждений сборки).
- Каждый пункт отвечает на три вопроса: **что** (тип/метод/ключ конфига), **где** (файл/слой), **эффект** (зачем / как меняется поведение).
- Изменения дефолтов конфигурации указываются явно; для ломающих изменений обязательна секция `Миграция`.
- Changelog пишется в том же PR, что и изменение, и входит в DoD релиза
  ([`05-definition-of-done.md`](./05-definition-of-done.md), п. 5.4).

## 4.7 Open Questions

Файл — `OPEN_QUESTIONS.md` в корне. Шаблон — [`docs/OPEN_QUESTIONS-TEMPLATE.md`](../../docs/OPEN_QUESTIONS-TEMPLATE.md).
Источник вопросов — раздел `## Open Questions` предложений ([`000-template.md`](../proposals/000-template.md))
и обсуждения с заказчиком.

**Правила:**

- Номер `OQ-N` — сквозной, **не переиспользуется**; закрытый вопрос переезжает в раздел «Закрытые», а не удаляется.
- Таблица: `| # | Вопрос | Решение | Статус |`; статусы `✅ закрыт (D-NNN)` / `⏳ открыт` / `❌ отклонён (D-NNN)`.
- В колонке «Решение» — **ответ пользователя** (агент готовит варианты и замеры, но не решает за заказчика).
- Для вопросов, влияющих на поведение, обязателен блок **замера** (методика, данные, выводы) до решения.
- Закрытие вопроса = запись в `DECISIONS.md` (`D-NNN`); при изменении поведения — ещё и запись в `CHANGELOG.md`.
- Открытые вопросы, влияющие на поведение, **блокируют релиз** (DoD 5.4).

## 4.8 Decisions

Файл — `DECISIONS.md` в корне. Шаблон — [`docs/DECISIONS-TEMPLATE.md`](../../docs/DECISIONS-TEMPLATE.md).
Журнал в формате **таблица + подробности**; архитектурно значимые решения дополнительно оформляются
как ADR (`docs/architecture/adr/`).

**Формат.** Шапка: `Формат: номер · дата · решение · статус · обоснование/источник.` и перечень статусов.
Основная таблица: `| # | Дата | Решение | Статус | Источник |`, где `#` — `D-NNN`; `Дата` — `YYYY-MM-DD`;
`Решение` — одна фраза (допускаются выделения и ссылки); `Статус` — `ACCEPTED` / `PROPOSED` /
`SUPERSEDED (D-XXX)` / `REJECTED`; `Источник` — `OQ-N`, предложение `<NNN-slug>`, стандарт `§X` или `.clinerules`.
Решения, не помещающиеся в строку, разворачиваются отдельными разделами
`## D-NNN — <заголовок> (подробности)` в конце файла: контекст, замеры, таблицы «механизм → что проверяет», следствия.

**Правила:**

- Номер `D-NNN` — сквозной, не переиспользуется: на него ссылаются `OQ-N`, `CHANGELOG.md`, код и ADR.
- Решение фиксируется **в момент принятия** (не задним числом).
- `PROPOSED` — решение ждёт подтверждения пользователя и **обязано** иметь парный `OQ-N` в `OPEN_QUESTIONS.md`.
- Отмена/замена — **новой** записью со ссылкой; старая помечается `SUPERSEDED (D-XXX)` и не удаляется.
- Порядок строк — хронологический; выбранный порядок держится по всему файлу.

## 4.9 Входные документы (inputs/)

Каталог — `inputs/` в корне. Правила — [`inputs/README.md`](../../inputs/README.md),
реестр — [`inputs/INDEX.md`](../../inputs/INDEX.md). Шаблон — [`docs/INPUTS-TEMPLATE.md`](../../docs/INPUTS-TEMPLATE.md).

**Что здесь.** Материалы, задающие требования: ТЗ и постановки (`briefs/`), концепции (`concepts/`),
макеты/примеры графики (`graphics/`), образцы данных и форматов (`samples/`).

**Правила:**

- Имя файла — `IN-NNN-<slug>.<ext>` (номер сквозной, не переиспользуется); группу файлов одного документа
  можно оформить папкой `IN-NNN-<slug>/`.
- Каждый материал регистрируется в `inputs/INDEX.md` (ID, файл, тип, дата, что задаёт, статус, где учтён).
  Материал без записи в реестре для процесса не существует.
- **Ссылка из спецификации** — Архитектор указывает использованные материалы в разделе `## Sources` предложения,
  по `IN-NNN`. Требование, не опирающееся ни на `inputs/`, ни на `OQ-N`/`D-NNN`, считается выдуманным (нарушение).
- **Оригинал не правится.** Изменение требований идёт через новое предложение и/или `OQ-N`; сам файл остаётся как был
  (неактуальное помечается `🗄 архив`, не удаляется).
- **Секреты и PII запрещены** (см. [`09-security.md`](./09-security.md)); крупные бинарники — обсудить Git LFS.
- Материалы влияют на спецификацию, но **не заменяют** её: источник требований ≠ спецификация.
- Документация, пришедшая из проекта, у которого уже была своя документация иной структуры, ведётся по §4.10.

## 4.10 Документация, существовавшая до внедрения SDD (чужая структура)

Каталог — `docs/legacy/` в корне.

**Что здесь.** Документация, которая уже была у проекта до внедрения SDD и устроена иначе: свои ADR,
ТЗ и постановки, `docs/` с другой иерархией, wiki/Confluence/Google Docs вне репозитория, исторические
и архивные документы, свой `CHANGELOG.md`. Раздел описывает, как такую документацию **учесть**, не
сломав её: сначала реестр и карта соответствий — только чтением, затем переносы и указатели — только
по утверждённым человеком строкам.

**Файлы:**

- [`docs/legacy/README.md`](../../docs/legacy/README.md) — правила ведения: назначение, словарь статусов,
  шаблон строки реестра, шаблон документа-указателя, маркер «оставить на месте»;
- [`docs/legacy/INDEX.md`](../../docs/legacy/INDEX.md) — реестр документов `LEG-NNN` и карта соответствий
  «их документ → наш артефакт»;
- [`docs/legacy/CHANGELOG-FROZEN.md`](../../docs/legacy/CHANGELOG-FROZEN.md) — приложение для той части
  истории изменений проекта до внедрения SDD, которая не переносится в проектный `CHANGELOG.md`
  (не дополняется).

**Правила:**

- **Реестр — вход всех решений по документации** (`LEG-NNN`, сквозной номер). Документ, которого нет
  в `docs/legacy/INDEX.md`, для процедуры не существует; карта соответствий «их документ → наш артефакт»
  ведётся только в реестре, без копии в других документах.
- **Реестр хранит метаданные, а не правила:** где документ живёт (путь или URL), чей он, кто им
  пользуется, актуален ли, какой наш артефакт ему соответствует, какое действие выбрано. Содержание
  документа в реестр не переносится.
- **Источник истины один.** Содержимое либо переносится в наш артефакт (`openspec/`, `docs/architecture/`,
  `docs/operations/`, `inputs/`), либо документ становится документом-указателем без нормативного текста.
  Два параллельных описания одного поведения недопустимы: при дубле строка останавливается и дубль
  докладывается, а не сводится молча.
- **Ничего не удаляется** (норма §4.9): перенесённое оставляет указатель; историческое остаётся на месте
  с маркером `🗄`; внешнее помечается `🌐` в реестре. Удаление — отдельное решение владельца, а не шаг
  процедуры.
- **Документация вне репозитория** — по умолчанию указатель: URL, владелец и причина в строке реестра.
  Выгружается только нормативное — то, что задаёт поведение или решение, — и не «страницей как есть»,
  а в наш артефакт (`inputs/` как `IN-NNN`, ADR, спека, runbook). Секреты, ключи и персональные данные
  не копируются ни при каких условиях (§4.9, [`09-security.md`](./09-security.md)).
- **Чужой `CHANGELOG.md` анализируется, а не копируется вслепую.** Каждая запись классифицируется:
  что ещё актуально — переносится в проектный `CHANGELOG.md` как датированная история с указанием
  источника (`LEG-NNN`), что устарело — остаётся приложением `docs/legacy/CHANGELOG-FROZEN.md`
  (дословно, без правки формулировок и дат) за одной строкой-указателем. Ничего не теряется: полное
  содержимое старого файла доступно либо в приложении, либо по исходному пути. Новые записи — только
  в проектном `CHANGELOG.md` с привязкой `(<ID>)` (§4.6).
- **Расхождение «документ vs код»** решается явно: код — фактическое поведение (baseline), документ
  помечается устаревшим или замещаемым, расхождение выносится в [`OPEN_QUESTIONS.md`](../../OPEN_QUESTIONS.md)
  как `OQ-N` с рекомендуемым значением по умолчанию (§4.7) и не решается молча
  ([`constitution.md`](../constitution.md) §1 п. 5).
- **Применение — только по утверждённым человеком строкам реестра**
  ([`constitution.md`](../constitution.md) §1 п. 2, §3 п. 1): инвентаризация и карта — чтение, переносы,
  указатели и маркеры — отдельный шаг с построчным утверждением; необратимые действия без утверждения
  не выполняются.
- **Проверка результата — «ответ за один переход»:** фиксированный список вопросов нового участника
  и таблица Pass/Fail с числом переходов, а не оценка «на глаз»
  ([`constitution.md`](../constitution.md) §1 п. 4). Машинно проверяется, что ссылки реестра резолвятся,
  у каждой строки есть артефакт или явное действие, архивные документы помечены, а указатели
  соответствуют шаблону и не содержат правил.
