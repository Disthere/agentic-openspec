# 07. Персистентность и данные

## 7.1 Модель и доступ

- **Database-per-service**: сервис владеет своей схемой; прямой доступ к чужой БД запрещён.
- Доступ — через EF Core (по умолчанию) или Dapper (горячие запросы). Никаких «магических» сырых SQL без параметров.
- Сущности БД **не выходят наружу**: контракт отдаёт DTO/модели.
- Миграции — версионируются и проверяются на обратимость (forward + rollback/backfill).

## 7.2 Транзакционные границы

- Одна бизнес-операция — одна транзакция (unit of work); не открываем транзакцию на весь запрос.
- Изменения между агрегатами — согласованность в конечном счёте (события/outbox), не распределённая 2PC-транзакция.
- Долгие операции не держат транзакцию/соединение открытыми.

## 7.3 Конкурентность

- Оптимистичная блокировка: токен версии/`RowVersion` + обработка конфликта (`409`/`412`, повтор).
- Никаких «read-modify-write» без защиты; критические инкременты — атомарно на стороне БД.
- Идемпотентность записи обязательна (см. [`06-api.md`](./06-api.md), [`08-messaging.md`](./08-messaging.md)).

## 7.4 Производительность запросов

- Чтение — `AsNoTracking()`; проекции (`Select`) вместо загрузки целых агрегатов.
- **Никакого N+1**: жадная загрузка/`AsSplitQuery` осознанно, либо проекция одним запросом.
- Пагинация обязательна для больших выборок; индексы — под фактические запросы (where/join/order).
- Тяжёлые/отчётные запросы — в холодном контуре (read model/реплика), не в горячем пути.

## 7.5 Ограничения и запреты

- Обход доменных инвариантов через прямой SQL без причины.
- `SELECT *`, отсутствие лимитов, unbounded-запросы на больших таблицах.
- Изменение схемы без миграции; миграции без плана на большие таблицы (lock/downtime).
