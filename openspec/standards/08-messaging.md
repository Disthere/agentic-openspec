# 08. Обмен сообщениями (messaging)

Применяется к асинхронному взаимодействию (Kafka/RabbitMQ) и событийной архитектуре.

## 8.1 Семантика доставки

- По умолчанию — **at-least-once**. Значит, обработчик **обязан быть идемпотентным**.
- Ровно-однократная обработка — через дедупликацию (ключ сообщения/идемпотентности), а не через «веру» в брокера.
- Публикация исходящих событий, согласованная с записью в БД, — через **transactional outbox** (и **inbox** на стороне получателя).

## 8.2 Идемпотентность

- Команда/событие несёт уникальный `MessageId`; повторная обработка не меняет результат.
- Для записей — проверка обработанных id (таблица dedup/inbox) в той же транзакции.

## 8.3 Порядок сообщений

- Порядок гарантируется **только внутри партиции/ключа** (partition key). Не полагаться на глобальный порядок.
- События одного агрегата — в одной партиции (по id агрегата).

## 8.4 Повторные попытки и обработка сбоев

- **Retry** с экспоненциальной задержкой и jitter, ограниченным числом попыток и бюджетом времени.
- **Poison/неисправимые сообщения** → dead-letter queue (DLQ); обработка DLQ — обязательна и наблюдаема.
- **Частичный отказ**: обработчик либо применяет эффект целиком, либо не применяет (без «полу-состояний»).
- Таймауты обработки; долгие обработчики не блокируют партицию бесконечно.

## 8.5 Контракты событий и SDD

- Схема события — часть контракта: имя, версия, поля, семантика. Хранится в `<предложение>/contracts/`.
- Эволюция — обратно совместимо (только добавление необязательных полей); ломающие изменения — по конституции (раздел 4).
- Подтверждение работы сценария — через [`10-observability.md`](./10-observability.md): метрики/трассы обработки, размер DLQ.

## 8.6 Запреты

- Приём сообщений без идемпотентности.
- «Молчаливое» проглатывание ошибок обработки; retry без лимита.
- Публикация события до коммита транзакции (без outbox).
