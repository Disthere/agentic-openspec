# Design — 004-desktop-profile

Как в один шаблон помещены два разных класса продуктов, чтобы правила не мешали друг другу.

## 1. Проблема

Серверный профиль требует того, чего у десктопа нет: открытых портов (health-checks), брокеров,
k8s-манифестов, серверных SLO. Десктопный продукт требует того, чего нет в серверном профиле:
правил UI-стека, локального рантайма моделей, шифрования локальной БД, единой точки выхода в сеть,
лицензионного инвентаря, бюджетов ресурсов.

Если сложить всё в один набор правил, получится худшее из двух: Ревьюер будет требовать k8s у десктопа
и отсутствие портов — у сервиса.

## 2. Решение: профиль как ось конфигурации

```
project.profile ─┬─→ schema (openspec/schemas/<profile>.yaml)     — что считается валидным предложением
                 ├─→ standards (01–11 [+ 12])                     — по каким правилам ревьюить
                 └─→ DoD sections (5.x)                            — что считать готовым
```

- `csharp-api` — как было: `csharp-api.yaml`, стандарты 01–11, DoD 5.1–5.7. **Ничего не меняется.**
- `csharp-desktop` — `csharp-desktop.yaml`, стандарты 01–11 + [`12-desktop.md`](../../../standards/12-desktop.md),
  DoD 5.1/5.2/5.5/5.6 + §5.8 (серверные 5.3/5.4 заменяются десктопным релизным чек-листом).
- Переключение профиля — решение (`DECISIONS.md`), а не молчаливая правка: иначе серверный проект
  внезапно начнёт валидироваться по десктопным правилам.

## 3. Что общего и что различается

| Общее (оба профиля) | Только серверный | Только десктопный |
| - | - | - |
| SDD-процесс: фазы, гейты, роли, `proposal.md`/`tasks.md`/`acceptance.md` | HTTP API, версионирование контрактов (06) | UI-стек и граница UI↔ядро (§12.2) |
| Стиль C# (01), архитектура (02), передачи (03), документация (04) | брокеры и доставка (08) | локальный рантайм моделей (§12.3) |
| DoD 5.1/5.2 (спека, код), 5.5, 5.6 (дискавери) | k8s/Docker/health-checks (5.3) | SQLite/SQLCipher/BIP39 (§12.4–12.5) |
| Принцип «измеряй, не заявляй» | серверные SLO (11) | бюджеты ресурсов (§12.8) |
| Тесты xUnit + архитектурные тесты | Runbook сервиса (5.4) | лицензионный инвентарь (§12.10), доказуемый egress (§12.9) |

## 4. Почему так, а не иначе

| Альтернатива | Почему отклонена |
| - | - |
| Один набор правил с пометками «применимо/нет» | Ревьюер всё равно сверяется с текстом; пометки в каждом пункте превращаются в шум и ошибки |
| Второй шаблон-репозиторий под десктоп | Дублирование процесса, фаз, ролей и пресетов; расхождение неизбежно |
| Десктопные правила отдельным стандартом **без** схемы и DoD | Схема задаёт обязательные разделы и гейты; без неё «правила» не проверяются |
| Отдельная роль под десктоп (Desktop-dev) | Роль без уникального артефакта и гейта не допускается (правило допуска из `002`): работу делает тот же `csharp-dev` по правилам профиля |

## 5. Риски

| Риск | Митигация |
| - | - |
| Расползание: правки профиля A ломают профиль B | серверные файлы не меняются (проверяется в acceptance: 01–11 и DoD 5.1–5.7 сохранены); правила профиля B живут в своих файлах |
| Правила-декларации без проверки | каждое правило стандарта 12 имеет проверку: тест, анализатор, гейт DoD 5.8 или артефакт (`licenses.md`, `performance.md`) |
| «Выбор профиля на глаз» | `project.profile` + решение в `DECISIONS.md`; схема и стандарт следуют выбору |
| Лицензионные риски стека (GPL/NC голоса, модели) | §12.10 + запрет в схеме + пункт релизного гейта |
| Числовые бюджеты выдуманы | до первого замера фиксируется метрика и способ замера; значения — `OQ-10` после замера на эталонном железе |
| Дрейф между схемой и стандартом | трассировка «требование → файл» проверяется в acceptance каждого предложения профиля |
