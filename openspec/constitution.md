# Конституция проекта

**Высший по приоритету документ.** При конфликте с любым другим документом (стандартами, инструкциями,
`.clinerules`, ролями) — действует конституция. Изменяется только отдельным утверждённым предложением.

## 1. Принципы

1. **Spec First.** Код не пишется и не меняется без спецификации в `openspec/proposals/`.
2. **Agree before you build.** Человек утверждает спецификацию до реализации.
3. **Traceability.** Каждое изменение кода трассируется к требованию (`<spec-id>`); разрыв трассируемости — дефект.
4. **Измеряй, не заявляй.** Утверждение «оптимизировано»/«выдержит нагрузку» без воспроизводимого замера недействительно.
5. **Никаких молчаливых решений.** Неоднозначность → зафиксировать вопрос и дефолт, не придумывать бизнес-правило.

## 2. Границы сервисов

- Один сервис — одна ограниченная область (bounded context) и **своя БД** (database-per-service). Общие таблицы запрещены.
- Взаимодействие между сервисами — только через **контракты** (gRPC/Protobuf, OpenAPI, схема сообщения). Прямой доступ к чужой БД запрещён.
- Публичные контракты (HTTP, gRPC, события) и границы сервисов **не меняются без согласованного плана**.
- Определение границ и их обоснование — в [`../docs/architecture/service-boundaries.md`](../docs/architecture/service-boundaries.md).

## 3. Обязательные проверки (гейты)

Ни один этап не пропускается:

1. **Spec gate** — спецификация создана и утверждена человеком.
2. **Build gate** — `dotnet build -c Release` без warnings.
3. **Test gate** — `dotnet test -c Release` зелёный; покрытие >80% (Domain >90%).
4. **Review gate** — независимое ревью (`Pass`) против спецификации, стандартов и DoD.
5. **Perf gate** — для изменений, влияющих на производительность: воспроизводимый нагрузочный сценарий и сравнение (см. [`standards/11-performance.md`](./standards/11-performance.md)).

## 4. Запрет несогласованных breaking changes

- Breaking change публичного контракта (поля, семантика ошибок, форматы) допускается **только** через новое предложение
  с планом миграции, версионированием и периодом совместимости.
- Нельзя «тихо» менять: версии SDK/зависимостей, схему данных, коды ошибок, семантику идемпотентности/повторов.

## 5. Порядок принятия исключений

Любое отклонение от стандарта оформляется так:

1. Записать проблему и обоснование в разделе `## Open Questions` / `## Impact` предложения.
2. Указать срок действия исключения и план возврата к стандарту.
3. Получить явное утверждение человека (владельца).
4. Зафиксировать исключение в [ADR](../docs/architecture/adr/) (или в самом предложении, если оно краткосрочное).

Без этих четырёх пунктов исключение не действует.
