# Сессия аудита SDD-набора — протокол запуска

**Назначение:** этот файл — для случая, когда цель сессии **не продукт**, а сам набор:
найти недостатки в SDD-концепции, проверить закрытие старых находок, найти новые.

> Обычная сессия (разработка продукта) начинается иначе — см. [`ADOPTION.md`](./ADOPTION.md) §2.
> Здесь — другой режим: **аудит, а не реализация**.

---

## Когда это нужно

- Замечаете, что правило в каноне не работает на практике.
- Хотите проверить, не разошлись ли документы после серии правок.
- Нужна ретроспектива: что из прошлого аудита действительно закрыто.
- Готовите набор к передаче и хотите найти дыры до получателя.

---

## Промпт для новой сессии

Скопируйте целиком в главную сессию с пресетом `sdd`.

> **Готовая версия с оговорками среды** (политика исполнения, отсутствие `pwsh`, поведение
> `dotnet test` в песочнице, обязательные негативные тесты гейтов) — в отдельном файле:
> [`sdd/docs/AUDIT-PROMPT.md`](./AUDIT-PROMPT.md). Он же содержит список мест, которые уже
> ломались, и что именно в них проверять.

```text
Ты — Оркестратор SDD. Задача этой сессии — АУДИТ САМОГО НАБОРА, не продукта.

Раскладка: всё SDD живёт в одной папке `sdd/`. В корне проекта остаётся только то, что
инструменты ищут строго там: AGENTS.md, .clinerules, .agents/ (DSH сканирует
<корень>/.agents/skills), .github/, global.json, Directory.*.props, .editorconfig.
Все пути ниже — от корня проекта. Пути в текстах — тоже от корня: так договорились.

Прочитай в таком порядке:
1. AGENTS.md — канон правил (§7.1: вопросы задаются вариантами ответов; §4 — раскладка)
2. sdd/openspec/constitution.md — высший приоритет, особенно §1 и §7
3. sdd/STATUS.md — где мы сейчас
4. sdd/docs/legacy/set-history/AUDIT-2026-11-12.md — прошлый аудит: 17 находок
   (5 P0, 7 P1, 5 P2), все P0 закрыты; там же §4 с доказательствами по каждой правке
5. sdd/docs/legacy/set-history/ASSESSMENT.md и PLAN.md — аудит позапрошлого цикла
   (11 P0, 21 P1, 33 P2) и план из 5 батчей: имей в виду, что часть выводов устарела,
   потому что набор с тех пор перестроен

Задача:
— проверь, что из прошлых находок действительно закрыто (не «по словам», а командой);
— найди новые недостатки: противоречия между документами, неработающие правила,
  декоративные гейты, дубли, устаревшие ссылки;
— проверь, что правила, добавленные ПОСЛЕ прошлых аудитов, соблюдаются
  (Spec First для продукта, §7.1 про варианты, STATUS.md, метрики);
— ОСОБО проверь последствия переноса в sdd/: пути в командах, в бэктиках и в промптах,
  работоспособность sdd/dsh/install.ps1 из нового места, сборку профиля.

Правила работы в этой сессии:
— сначала факты командами (sdd/tools/*.ps1, docs/ci/check-dsh-profile.ps1, git log), потом выводы;
— в этой среде .ps1 блокируются политикой RemoteSigned: запускай через
  powershell -NoProfile -ExecutionPolicy Bypass -File <путь>; pwsh не установлен;
  dotnet test падает на named pipes песочницы (это НЕ дефект набора — проверяй
  прямым запуском артефакта), dotnet restore требует сети;
— каждую находку подтверди воспроизведением, укажи файл:строку;
— у каждого гейта проверь НЕГАТИВНЫЙ тест: подложи дефект и убедись, что гейт падает;
— ничего не меняй без моей команды;
— вопросы ко мне — вариантами ответов (AGENTS.md §7.1).

Формат результата:
1) таблица «находка → приоритет → улика → куда чинить»;
2) отдельно: что из прошлых аудитов НЕ закрыто и почему;
3) отдельно: новые находки с приоритетом;
4) отдельно: что нового сломал перенос в sdd/, если что-то сломал.

Не начинай правки. Сначала отчёт.
```

## Ключевое правило этой сессии

**Правки набора не требуют полного SDD-цикла.** Это зафиксировано в
[`sdd/openspec/constitution.md`](../openspec/constitution.md) §1 п. 7:

| Что меняется в наборе | Как оформляется |
| - | - |
| Канон, стандарты, документация процесса | запись в `sdd/docs/legacy/set-history/` + сообщение коммита |
| Пресет DSH, роли, конфигурация | то же + `docs/ci/check-dsh-profile.ps1` зелёный |
| Инструменты `sdd/tools/*.ps1` | то же + прогон инструмента и **негативный тест** |
| Схемы, шаблоны предложений | то же + `sdd/tools/validate-proposals.ps1 -All -Archived` |

Обязательны всегда: **проверка командой, негативный тест гейта, осмысленный коммит**.
Фиктивная спецификация вместо этого — нарушение, а не «строгость».

> **Почему записи идут в `sdd/docs/legacy/set-history/`, а не в `DECISIONS.md`.** Реестры — часть шаблона,
> при раздаче они сброшены к пустым формам. История набора в них уедет в чужой проект.

### Второе ключевое правило: решения — диалогом, а не таблицей в отчёте

Аудит почти всегда находит пункты, где выбор принадлежит владельцу: оставить долг или закрыть,
менять поведение гейта или нет, какой из профилей активный. **Эти пункты задаются диалогом
с вариантами** ([`AGENTS.md`](../../AGENTS.md) §7.1, конституция §1 п. 6), а не таблицей
«вариант → следствие» в конце отчёта.

| Правильно | Неправильно |
| - | - |
| Отчёт с находками → отдельный диалог на каждое решение (2–4 опции, первая — рекомендуемая) | Отчёт → «вот варианты A/B/C, скажите какой» в прозе |
| Решение зафиксировано: ответ → `D-NNN`/запись в `set-history`, `OQ-N` закрыт | Решение осталось в переписке сессии |
| Развилка, не блокирующая работу → `OQ-N` с дефолтом, работа продолжается | Остановка работы ради вопроса, у которого есть безопасный дефолт |

**Почему это записано отдельным пунктом.** На аудите 2026-11-16 два решения владельца были
предложены таблицей в тексте отчёта: формально «варианты были», фактически диалога не произошло —
владельцу пришлось отвечать вручную и указать на дефект. Формулировка правила соблюдалась
буквально и нарушалась по сути.

## Гейты, которые должны быть зелёными в конце

```powershell
.\sdd\tools\validate-proposals.ps1 -All -CheckLinks
.\sdd\tools\validate-proposals.ps1 -Archived
.\sdd\tools\validate-proposals.ps1 -Templates      # шаблон 000-* верен ПОСЛЕ копирования
.\sdd\tools\check-canon-parity.ps1
.\sdd\tools\check-template-clean.ps1
.\sdd\tools\register-inputs.ps1 -Check
.\sdd\docs\ci\check-dsh-profile.ps1
dotnet build --configuration Release --no-restore
dotnet format --verify-no-changes
```

> **Если Windows отвечает `is not digitally signed` или `AuthorizationManager check failed`.**
> Это ограничение **вашей машины/политики**, а не дефект набора. Проверено на машине аудита
> (`Get-ExecutionPolicy -List` → `CurrentUser = RemoteSigned`): при такой политике скрипты набора
> **не запускаются** — `RemoteSigned` пропускает локальные файлы без метки «из интернета» только
> в теории, на практике `.ps1` без подписи отклоняется с `UnauthorizedAccessException`.
> Поэтому запускайте через `-ExecutionPolicy Bypass`, это штатный обход без прав администратора:
>
> ```powershell
> powershell -NoProfile -ExecutionPolicy Bypass -File .\sdd\tools\validate-proposals.ps1 -All -CheckLinks
> ```
>
> Тот же приём используют сами гейты, когда вызывают друг друга
> (`check-template-clean.ps1`, `collect-metrics.ps1`, `check-dsh-profile.ps1`), и `sdd/dsh/install.ps1`
> в инструкции установки. В CI на ubuntu ограничения нет.

Плюс собрать метрики: `.\sdd\tools\collect-metrics.ps1 -WithGates -OutFile sdd/METRICS.md`.

## Чего делать НЕ надо

- Не начинать с правок. Сначала отчёт с уликами.
- Не доверять `STATUS.md` на слово — сверять с `sdd/openspec/proposals/`.
- Не считать «зелёный гейт» доказательством: у каждого скрипта есть негативный тест, проверьте, что он падает.
- Не переписывать стандарты 01–12 по содержанию — они вне объёма аудита набора.
